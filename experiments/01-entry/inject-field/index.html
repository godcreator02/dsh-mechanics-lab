01-entry / inject-field

条目级 inject 是补充，不是覆盖

两处都能声明依赖、内容不一样时，dsh 听谁的——这一项拿一次实测钉死答案。

档次 ② 🔬 发现型 ✅ 1 条用例 不需要 web

这一项讲的是什么

一条条目（entry，见 00-base/baseline-profile）除了 id / name / config，还能写一个 inject 字段——一份服务名清单， 管这条条目激活前要等哪些服务（service）先就位。插件包自己也能这样声明依赖：模块顶层 export const inject = [...]，这是官方文档教的主流写法，好处是依赖跟着代码走， 别人挂这条插件时不用记得在条目上重写一遍。两处都能写，内容不一样时 dsh 到底听谁的——这一项 就是要把这件事钉死。

机制怎么工作

条目级、代码级两处都能声明依赖——挨个点开看它们各自是什么、依赖门槛怎么生效、 本项具体怎么把两处摆成冲突的。

两条路，dsh 走了哪条

条目上给 lab-alpha 写的是 inject: []（清空），代码里却声明着 ["labRegistry"]——点开两张卡看每条路径接下来会发生什么，标着「✓ 实测」的 那张才是真的发生过的。用例 test_entry_level_inject_is_additive_not_override。

条目上写的（cordis.patch.yml 节选）
    - id: lab-alpha
      name: lab-alpha
      inject: []
账本记下的（ledger.json · entries[0]，归档 20260817-151109）
who"lab-alpha" ms5.4318 at2026-08-17T07:11:08.638Z

ms 是相对 lab-registry 自己 apply 起算的耗时 （process.hrtime.bigint() 打点，见右侧 fixtures/lab-registry/index.js） ——量的是「provide 服务的插件」和「消费它的插件」之间隔了多久，不是绝对时钟。组合树里这条目的 inject 字段也确实是 []——用例另外用 dump_config 断言过 （同一条用例第 84 行）。条目级声明没被静默吞掉，它原样进了组合树，只是没能削弱代码里的依赖声明。

①

条目上的 inject 是补充，不是覆盖。组合树里 lab-alpha 的 inject 确实是 []，但插件照常等 labRegistry 服务就位才 apply。 想靠条目级 inject 绕开代码里的依赖声明，行不通。 test_entry_level_inject_is_additive_not_override

②

判定看账本里有没有那一笔，不看进程死没死。账本每登记一笔就整份落盘，顺序就是真实的 apply 先后；lab-alpha 拿不到服务时也不会抛错，而是照实记录 gotRegistry: false ——这条口子探针留着，本次没触发，因为账本本身已经能把「inject 没满足→根本没 apply」和 「apply 了但服务是 undefined」这两种现象分开。 test_entry_level_inject_is_additive_not_override · 模块 docstring「观测方法」

⚠

只有这一条用例撑着。验的只是「条目级清空 + 代码级声明」这一种组合——条目级写非空数组 会不会追加、代码完全不声明依赖时条目级 inject 能不能单独生效，都还没验。看到「1 条用例」 要按这个量级读，不要当成跟满覆盖的项一样确凿。

判定与证据出处在 test_inject_field.py 的模块 docstring，此页只负责让你看懂。

/**
 * 依赖链的根：提供 `labRegistry` 服务，一本「谁来登记过」的账本。
 * 它自己不依赖任何人，是本项唯一需要的服务提供者。
 *
 * 账本每登记一笔就整份落盘，所以见证文件里的顺序就是实际的 apply 顺序。
 */

import { writeFileSync } from "node:fs";

const MARKER = "lab-registry-v1";

export function apply(ctx, config) {
  const ledger = config?.ledger;
  if (!ledger) throw new Error("lab-registry: config.ledger（账本落盘路径）是必需的");

  const entries = [];
  const t0 = process.hrtime.bigint();

  const dump = () =>
    writeFileSync(
      ledger,
      JSON.stringify({ marker: MARKER, providedAt: new Date().toISOString(), entries }, null, 2),
      "utf8",
    );

  const book = {
    sign(who, note) {
      entries.push({
        who,
        note: note ?? null,
        ms: Number(process.hrtime.bigint() - t0) / 1e6,
        at: new Date().toISOString(),
      });
      dump();
    },
    list() {
      return entries.slice();
    },
  };

  // ctx.provide 返回一个 disposer；fiber 卸载时服务自动撤销，
  // 所以这里不用自己 ctx.effect 包——provide 本身就是个 effect。
  ctx.provide("labRegistry", book);

  // 先落一次空账本：证明「服务提供者自己先到位」这件事
  dump();
}

  "version": "0.0.0",

/**
 * 依赖 `labRegistry` 的消费者。依赖声明写在**插件代码里**——这是主流写法，
 * 条目上也能写（本项就是要验条目级 `inject` 与代码级声明的关系）。
 */

import { writeFileSync } from "node:fs";

const MARKER = "lab-alpha-v1";

export const inject = ["labRegistry"];

export function apply(ctx, config) {
  const book = ctx.get("labRegistry");

  // ⚠️ 拿不到服务时不抛错，如实记录。探针在观测点抛错会把两种完全不同的
  // 现象混成一种：「inject 没满足 → 根本没 apply」 vs 「apply 了但服务是
  // undefined」——前者见证文件不出现，后者见证文件出现且 gotRegistry=false，
  // 必须能分开。
  if (book) {
    book.sign("lab-alpha", config?.note ?? null);
  }

  if (config?.witness) {
    writeFileSync(
      config.witness,
      JSON.stringify(
        {
          marker: MARKER,
          appliedAt: new Date().toISOString(),
          gotRegistry: book !== undefined && book !== null,
          config,
        },
        null,
        2,
      ),
      "utf8",
    );
  }
}
