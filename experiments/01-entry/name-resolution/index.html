01-entry / name-resolution

条目的 name 怎么变成一个真的模块

条目里 name 写的那个字符串，怎么被 loader 变成一次真正的模块加载——同一个字段，实测下来只有两条互不相通的解析算法，各自的规则、各自的边界。

档次 ① ⚠️ 矫正型 ✅ 满覆盖 · 11 条用例（4 个参数化） 不需要 web

这一项讲的是什么

条目（entry，见 00-base/baseline-profile）有个 name 字段：loader 拿它去问 Node「这个字符串对应哪个模块」，问到了就把模块 import 进来、执行它的 apply。这一项讲的正是 这一步——name 里写的那个字符串，怎么被 dsh 的 loader（cordis-plugin-loader 的 EntryTree.import）变成一次真正的模块加载。同一个字段，源码里判了四种写法，实测下来它们 分走的其实只有两条解析算法，各自的规则、各自的边界，写错一步就从「能被 Node 读懂的字符串」 变成「读不懂的字符串」。

机制怎么工作

走一遍 EntryTree.import 判断这个字符串该怎么读的过程：①②是各自独立的分支， ③④决定剩下的字符串最终走哪条解析算法，⑤是这两条算法各自认的锚点。

地基：internal 是不是激活

后面每一条判定的因果解释，都先看这一个字段——如果它激活，③④会被同一次调用接管。 见证探针（fixtures/probe）在自己那三个指纹之外，多测一件事： ctx.get("loader").internal !== undefined。这条探针本身走裸包名加载，能不能测到这个 字段跟"internal 是否激活"这个问题本身正交，可以放心当第一条用例。

本次部署上它是激活的——③④两条实际上都被同一次 internal.import(name, baseUrl, {}) 调用接管，name 原样传入，不做任何前缀判断。 表现出来的规则跟源码注释里写的③④分支基本一致（报错堆栈里能看到 Node 内部 ESM loader 的函数名）， 所以下文仍按③④两条来讲。

读出来的是什么

①

internal 已激活，"三条互不相通的解析路径"只成立一半。ctx.loader.internal 本次实测激活——相对路径 / 绝对路径 / 裸包名全部经同一条 internal.import(name, baseUrl, {})，cordis: 前缀在它之前就短路，是独立的第一刀。 test_loader_internal_activated

②

矫正点：官方文档说「插件路径必须是绝对路径」，实测规则是「必须是合法 URL」。 官方 docs/official/zh/user/develop/basic/index.md:56：“插件路径必须是绝对路径。patch 文件只贡献配置，不会改变 loader 解析模块路径时使用的 profile 目录。”示例给的是 POSIX 风格路径—— POSIX 上「绝对路径」恰好同时是合法 URL 路径部分，文档的建议不会踩坑；但 Windows 裸盘符路径 （D:\…）不是合法 URL，D: 被当协议名解析，报 ERR_UNSUPPORTED_ESM_URL_SCHEME；同一份文件写成 file:// URL 就能加载。 文档没有区分操作系统，这是「建议」和「解析规则」之间的落差。 test_windows_absolute_path · test_file_url

③

两种「加载失败」，报错文本完全不同。cordis: 未知内置表项是 cordis 自造的报错 （从没建立过 fiber）；裸包名指向不存在的包走的是 Node 标准的包解析失败。两者都表现为「启动失败」， 但成因不同，不能只判断「有没有报错」。 test_cordis_unknown_builtin · test_nonexistent_bare_package

④

exports 声明的子路径才能被包解析找到，未声明的哪怕文件确实存在也会 ERR_PACKAGE_PATH_NOT_EXPORTED。 test_exports_subpath[declared] · test_exports_subpath[undeclared]

⑤

包解析的边界不在 exports，而在「Node 能不能 resolve 到入口」。 exports["."] → main → 默认 index.js，三条路任意一条通就能加载， 只有三条全断才真的加载不了。 test_resolution_is_the_real_boundary（4 个变体）

⑥

相对路径没有这条回退链。同一份代码：回退路全断时包名到不了，相对路径直指同一个文件照样能 加载——回退链只属于包解析，相对路径走的是纯 URL 解析，压根不看 package.json。 test_relative_path_has_no_fallback_chain

⑦

裸包名以 dsh 安装目录为锚，不必 link 进 profile。timer/hmr 从没被 link 过，标准 Node parent-walk 在上一层的共享 node_modules 里就能找到。 test_bare_package_name_resolves_via_shared_node_modules

⑧

相对路径指到目录会失败，指到文件才行。name.startsWith(".") 走 import(new URL(name, ctx.baseUrl))，指到目录报 ERR_UNSUPPORTED_DIR_IMPORT—— 只有包解析认 package.json，相对路径压根不看它。 test_relative_name_resolution[指向目录] · test_relative_name_resolution[指向文件]

⑨

对照组：同一份文件，name 写对了就跑了。排除「插件本身有毛病」这种可能——前面 所有失败都只跟 name 本身有关，不是文件的问题。 test_correct_relative_name_just_runs

判定与证据出处在 test_name_resolution.py 的模块 docstring，此页只负责让你看懂。

/**
 * 通用探针：除了 marker / moduleLoadedAt / appliedAt 三个指纹，多探一件事——
 * `ctx.get("loader").internal` 是否激活。
 *
 * 这件事优先级最高：`cordis-plugin-loader` 的 `EntryTree.import` 里，`internal`
 * 分支排在最前面。如果它激活，相对路径 / 绝对路径 / 裸包名全部走同一条
 * `internal.import(name, baseUrl, {})`（name 原样传入，不做任何前缀判断），
 * 那"三条互不相通的解析路径"的说法就不成立——本项后面每一条用例的因果解释，
 * 都要先看这个字段才知道该往哪个分支上挂。
 *
 * 这个插件本身通过裸包名被加载，所以它自己的加载成功与否不受这个问题影响，
 * 可以放心当第一条用例。
 */

import { writeFileSync } from "node:fs";

const MARKER = "name-resolution-probe-v1";
const moduleLoadedAt = new Date().toISOString();

/** 观测点绝不抛错：拿不到就如实记 null。 */
function safe(fn) {
  try {
    const v = fn();
    return v === undefined ? null : v;
  } catch {
    return null;
  }
}

export function apply(ctx, config) {
  const witness = config?.witness;
  if (!witness) throw new Error("probe: config.witness 是必需的");

  const loader = safe(() => ctx.get("loader"));

  writeFileSync(
    witness,
    JSON.stringify(
      {
        marker: MARKER,
        moduleLoadedAt,
        appliedAt: new Date().toISOString(),
        // ctx.loader.internal 是否激活——决定 name 解析走哪条分支
        loaderInternal: loader ? safe(() => loader.internal !== undefined) : null,
        // ctx.baseUrl 是相对路径解析的锚点，顺手记一笔
        baseUrl: safe(() => String(ctx.baseUrl ?? "")),
        config,
      },
      null,
      2,
    ),
    "utf8",
  );
}

/**
 * 拍一张运行时快照的教学插件：给「裸包名 / 相对路径的 name 到底解析到了
 * 没有」这个问题提供一个比见证文件更直接的信号——settle 快照里能看到
 * timer / hmr 是不是真的到了 ACTIVE。
 *
 * 延后用 Node 原生 setTimeout，不用 `ctx.setTimeout`——后者是 timer 服务
 * 提供的，而 timer 在不在正是要测的东西，拿被测对象当测量工具会循环论证。
 */

import { writeFileSync } from "node:fs";

const MARKER = "census-v1";

function censusEntry(entry) {
  const fiber = entry.fiber;
  return {
    id: entry.options?.id ?? null,
    name: entry.options?.name ?? null,
    fiberState: fiber === undefined ? null : fiber.state,
  };
}

export function apply(ctx, config) {
  const out = config?.out;
  if (!out) throw new Error("census: config.out 是必需的");
  const delayMs = config?.delayMs ?? 1500;

  const flush = (entries) =>
    writeFileSync(out, JSON.stringify({ marker: MARKER, at: new Date().toISOString(), entries }, null, 2), "utf8");

  const handle = setTimeout(() => {
    const loader = ctx.get("loader");
    flush(loader === undefined ? null : [...loader.entries()].map(censusEntry));
  }, delayMs);
  ctx.on("dispose", () => clearTimeout(handle));
}

/**
 * 包解析的回退链是 exports["."] → main → 默认 index.js，三条路任意一条通就能
 * 被包名 resolve 到。这个包故意三条全断——没有 exports、没有 main，真正的
 * 代码又不叫 index.js（叫 plugin.js）。
 *
 * 用途：证明相对路径没有这条回退链。同一份代码：用包名引用（走 package.json
 * 解析）应当失败；用相对路径直接指到这个文件（走纯 URL 解析，不看
 * package.json）应当成功。
 */
import { writeFileSync } from "node:fs";

const MARKER = "fallback-plugin-v1";

export function apply(ctx, config) {
  const witness = config?.witness;
  if (!witness) throw new Error("fallback/plugin: config.witness 是必需的");
  writeFileSync(
    witness,
    JSON.stringify({ marker: MARKER, appliedAt: new Date().toISOString() }, null, 2),
    "utf8",
  );
}
