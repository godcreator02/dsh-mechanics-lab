01-entry / disabled

关掉一条条目

写了 disabled，条目还在树上，只是没人替它建 fiber——跟压根没写这一条， 长得几乎一样，树上的存在与否却完全不同。

档次 ① 📗 复述型 🔬 发现型 ✅ 6 条用例（4 个参数化） 不需要 web

这一项讲的是什么

配方（recipe）里的每一行是一条条目（entry）：写着挂哪个插件、给它什么配置； 它在运行时对应一个 fiber——这个插件这一次生命的载体。条目可以再挂一个 disabled 字段，写 true 或者一段延迟求值的表达式，告诉框架 「这一条先别挂」。这一项要讲清楚的，是「不挂」具体是什么样子：它不是把这一行 从配方里抹掉——条目照样留在组合树里，--dump-config 找得到它、patch 还能 按 id 定位它；只是激活那一步被跳过，没有人替它建 fiber，它的 apply 一次 都不会跑。同一件「没声音」的背后，「写了但关掉」跟「压根没写这一条」是两种完全不同的 树形状态——这条边界就是这一项要立住的东西。

机制怎么工作

跟着 1 → 5 走一遍：从写法，到条目激活那一刻框架真正做的事。

静态开关：dump 看得见，apply 不跑

用例 test_disabled_keeps_entry_in_tree_but_skips_apply， profile static-off——先看最直接的写法：布尔字面量 true。

static-off 的 cordis.patch.yml
# disabled 活层
- insert:
    - id: lab-entry
      name: lab-entry
      disabled: true
      config:
        witness: "D:/dshfiles/26081520anu/dsh-mechanics-lab/out/testhome/disabled/w-disabled.json"
✅ dump 视角：dump.require("lab-entry") 找到了这一条， disabled 字段是 true——条目还在树里。
apply 视角：固定等了 12 秒（验证「不会发生」不能靠轮询提前退出）， 见证文件 w-disabled.json 没有出现——它没跑。
条目在组合树里、disabled=True，apply 未执行——禁用 ≠ 删除。

!!js 表达式：什么时候求值

disabled 除了布尔字面量，还能写一段延迟求值的 !!js 表达式——DSH include 层的 YAML 方言。两组对照，问的是同一件事： 这段表达式是不是真的在条目激活时才被求值，不是解析时就死成了一个值。前两张卡片是 它的真实用途（按平台条件禁用）；后两张卡片专门对照官方事故复盘 postmortem 0002 记录过的一次旧 bug。

写了但关掉，跟压根没写——两种不同的树

同一件事换一个观测角度：不再靠见证文件问「apply 跑没跑」，改用 lab-recorder（订阅 Cordis 生命周期事件的采集器）把条目的树上位置、有没有 fiber、走没走状态整个记下来。教学插件也换了一个——worker.mjs，靠 inject: ["labObserver"] 自己上报一句话。三张卡片摆的是同一个条目 id （worker）在三份 profile 里的样子。

on 和 off-cmp 之间隔着「有没有 fiber」；off-cmp 和 absent 之间隔着「在不在树上」。写了但关掉的那一张卡片——两条线都不占： 不像 on 那样有 fiber，也不像 absent 那样连树上都找不到它。
另一条用例（test_disabled_entry_stays_in_tree_without_fiber， profile off）补了一个必要的对照：同一次运行里，紧挨着 worker 的 timer 老老实实从 LOADING 走到了 ACTIVE（约 2.05ms）—— 证明不是「采集器睡着了」，是 worker 真的没被建 fiber。

①

disabled: true 是不挂载，不是删除。条目仍在组合树里——dump 找得到、patch 还能按 id 定位它；只是 apply 不执行。删除之后的行为是另一回事 （见 02-recipe / override-semantics），跟禁用不是一回事：禁用可逆，删除不是。 test_disabled_keeps_entry_in_tree_but_skips_apply

②

写了但关掉 ≠ 压根不写。前者在树上、没有 fiber；后者连拍都拍不到， 事件流里连名字都不出现。两边都是「一句话没说」，光看「跑没跑」分不出这两种 情况——得看它在不在树上。 test_disabled_entry_stays_in_tree_without_fiber · test_disabled_differs_from_absent_entry

③

去掉那一行、重启，条目立刻恢复正常。和关掉那份 patch 只差 disabled: true 这一行，连 config 都一字不改。 test_removing_disabled_flag_restores_apply

④

!!js 表达式在条目激活时才求值，不在 dump 时。平台条件两个变体在同一台 机器上结果相反；对照官方事故复盘 postmortem 0002 记录的旧 bug（表达式被解析成 对象、对象恒真，受影响插件永远判定为禁用），当前 disabledOf() 确实对表达式求值——那次 bug 在当前版本不复现。 test_disabled_platform_conditional_expression · test_disabled_boolean_expression_matches_current_behavior

⑤

祖先禁用会不会连带子条目——不在这一项里。本项只验证条目自身的 disabled；沿父链向上传播（祖先禁用则子条目不运行，group 自己不受 影响）属于 02-recipe / 07-tree 的树形结构问题。 本项不覆盖范围外

判定与证据出处在 test_disabled.py 的模块 docstring，此页只负责让你看懂。

/**
 * disabled 用的教学插件：写见证文件证明 apply 执行过，外加回显运行平台——
 * 用来验证 `disabled` 写成 `!!js` 表达式时的条件求值确实按平台生效。
 */

import { writeFileSync } from "node:fs";

const MARKER = "disabled-v1";
const moduleLoadedAt = new Date().toISOString();

export function apply(ctx, config) {
  const witness = config?.witness;
  if (!witness) {
    throw new Error("lab-entry: config.witness 是必需的");
  }

  writeFileSync(
    witness,
    JSON.stringify(
      {
        marker: MARKER,
        moduleLoadedAt,
        appliedAt: new Date().toISOString(),
        platform: process.platform,
        config,
      },
      null,
      2,
    ),
    "utf8",
  );
}

 * lab-recorder 才能看到，见证文件做不到。
 */

export const inject = ["labObserver"];

export function apply(ctx, config) {
