03-supply / four-ways

四条供给路径，挂出同一个条目

把插件代码送到 profile 能找到的位置——本项试了单文件拷贝、目录链接、走官方安装命令、指向 git 工作副本四种姿势。只要挂载那步真的发生，四条路挂出来的条目在运行时没有任何区别，各自留下的代价却差得很远。

档次 ① 📗 部分复述 🔬 发现型 ✅ 满覆盖 · 3 条用例 不需要 web

这一项讲的是什么

一个插件要真的在 dsh 里跑起来，两件事缺一不可：配方树里得有一条 entry 指向它——挂载，02-recipe/insert-semantics 讲过的姿势，靠 - insert: 写活层；entry 的 name 字段还得能被 Node 解析到真代码——01-entry/name-resolution 讲过的两条解析算法。这两条链条共同的前提是：那份被解析到的代码，首先得摆在 Node resolve 得到的地方。这一项讲的正是这件更前置的事——供给：一个 npm 包（教学插件 ch2-courier，见侧栏它的三份文件）能用几种不同姿势，把自己的代码交付到 profile 能找到的位置，以及这几种姿势挂出来的条目，运行时表现有没有区别。

机制怎么工作

走一遍四条路怎么把 ch2-courier 送到 profile 上：①是两条线索怎么分工，②③是供给的四种实现各自怎么办，④是供给方式跟运行时结果之间的关系，⑤补全「两件事缺一不可」这句话的另一半。

观测方法：四个独立实例，只看插件自己说了什么

判据全部落在 ch2-courier 自己上报的内容上——通过 labObserver（00-base/recorder-reach 讲过的观测服务）——不看树的其它部分：条目在不在树上、走过哪些状态、说过什么话、报出来的 config、条目上的 name。四条路各起一个独立的 dsh 实例（一条路一个 profile，互不干扰），各自等 ch2-courier 说话，再把四份观测横向摆在一起对比；第五个 profile（notinstalled）不手写 insert、也不跑安装命令，作负对照。

四个 profile 各自独立起一个实例，等 ch2-courier 自己上报，再横向对比。除了条目上的 name，其余全部一致——供给方式没有漏进运行时。

③正经安装是唯一「包自己声明要挂哪个条目」的一条——代价是它会改写 profile 的 package.json（dsh.profile.bundles 多出一项、node_modules 里多出 pnpm 自己的记账文件），而且是唯一一个活层 cordis.patch.yml 不用写 courier 这个 id 的。

对照组：包在，但没装也没写

notinstalled profile 跟 linked 走的是同一份代码，同样建好了 ch2-courier 的 junction（侧栏可查看它的三份文件，跟 linked 逐字节相同）——唯一的差别是活层没有手写那句 - insert:，dsh.profile.bundles 也没有它的名字。

包目录里那份 cordis.patch.yml（侧栏可点开）没人会去读它——供给这一步单独做好，不会让条目凭空出现在树上。

读出来的是什么

①

四条路挂出来的条目没有任何区别。差别只落在条目自己的 name 上——单文件写相对路径，其余三条写包名。 test_four_ways_mount_the_same_entry

②

apply 早于 ACTIVE 这条判定，寄居在同一张对比表里。四条路的 apply 全都跑在该条目变 ACTIVE 之前；以后要找这条判定，grep apply 早于 ACTIVE。 test_four_ways_mount_the_same_entry

③

四条路的代价差得很远。要准备的文件、profile 目录里留下的东西、要不要手写活层 insert，各不相同——见上方「各自的代价」。 test_four_ways_mount_the_same_entry

④

包摆在那儿，不装也不写，什么都不会发生。自注册靠的是「装」这个动作，不是「包目录里躺着一份 patch 文件」。 test_the_package_alone_registers_nothing
