03-supply / pinned-worktree

依赖指向一份钉住的 git 工作副本，换 tag 即换版本

profile 的依赖不一定要指向一个只会被手改的静态目录——指向一份钉在某个 git tag 上的工作副本一样能被当成插件加载；开发照常在另一份跟着 HEAD 走的副本里继续，发一次版就是让钉住的那份副本切一次 tag，热重载把新代码原地挂上，进程不重启。

档次 ① 🔬 发现型 ✅ 满覆盖 · 3 条用例 不需要 web

这一项讲的是什么

这一组（03-supply）讲的是插件代码怎么「供给」进一个 profile——条目（entry，见 00-base/minimal-profile）的 name 指向一个包名，那个包在磁盘上真正的文件从哪儿来，是这一组要回答的问题，跟 name 字符串本身怎么被解析（那是 01-entry/name-resolution 管的）是两件事。profile 通过 package.json 的 dependencies 用 link: 协议指向一个目录，node_modules 下建一条 junction（Windows 的目录重解析点，见 00-base/isolation-guarantees）——这条路径本身没什么特别，特别的是这一项要试的目标目录：不是一份普通的源码目录，而是用 git worktree（git 自带的功能：同一个仓库能在别的目录下再开一份独立的工作副本，各自签出到不同的提交，文件互不干扰，但共享同一份提交历史）开出来的一份工作副本，还钉在某个 tag 上，不跟着分支走。这一项讲的正是：依赖指向这样一份「钉住」的工作副本会发生什么，以及在这条供给方式下，「发一次版」具体对应哪个动作。

机制怎么工作

从「同一个仓库的两份工作副本」到「profile 的依赖指向哪一份」到「文件真的换了会被谁接住」，走一遍这五步：①②搭好两份互不干扰的工作副本，③是依赖怎么落地成 profile 能读到的东西，④是文件被换掉之后谁在看、看见了做什么，⑤是这条链路里唯一真正算「发版」的那个动作。

现场：一个仓库，三份钉住的工作副本

整个实验只有一个 git 仓库（repo/，跟着 HEAD 走）。三条用例各自用 Repo.pin()（git worktree add --detach <目录> v1.0.0）从它开出一份独立的、钉在 v1.0.0 上的工作副本，各用各的，互不干扰。profile 的依赖不指向右栏的 fixtures/——它指向这样一份工作副本，node_modules 里那条 junction 落到的正是下面这几个目录之一。

$DSH_HOME/ ├─ repo/ 跟着 HEAD 走的开发副本——此刻在第二版 ├─ pinned-a/ 钉在 v1.0.0，a-pinned 这个 profile 的依赖指向它 ├─ pinned-b/ 钉在 v1.0.0，测试中途 checkout 到 v2.0.0 ├─ pinned-d/ 钉在 v1.0.0，全程没人碰它 └─ profiles/ └─ <profile>/node_modules/greeter → junction，指到上面对应的 pinned-* 目录

这几份工作副本本身不在归档范围内（results/ 只留了每个 profile 的三份文件，见右栏），但此刻的内容可以确定：copy_version() 把 fixtures/v1（或 fixtures/v2）的文件原样复制进 repo/、提交、打 tag，仓库关掉了 core.autocrlf——git checkout 出来的正是提交时的那份字节，所以 pinned-a 与 pinned-d 此刻的四个文件与右栏 fixtures/v1 逐字节相同，pinned-b checkout 到 v2.0.0 之后与右栏 fixtures/v2 逐字节相同。

怎么测：三个字段来自三个不同的文件

教学插件 greeter（右栏 fixtures/v1 与 fixtures/v2）说的话固定带三个字段——版本号来自 package.json 与 version.js，招呼语来自 greeting.js，入口来自 index.js 自己写死的字符串。三个字段来自三个不同的文件，换版本只换了一半的话，这里立刻能看出来。判「热重载」还是「重启」看事件流里的 status 事件与进程 pid：pid 不变、旧条目走过 DISPOSED，才是热重载。

依赖指向工作副本，插件照常加载——认的是 tag 不是 HEAD

钉在 tag 上的副本v1.0.0
插件说的{'版本': '1.0.0', '招呼语': '早上好', '入口': '第一版'}
耗时1.47s

此刻仓库主线已经在第二版（c71eb0a），但依赖指向的是钉在 v1.0.0 上的那份副本——插件仍然报第一版。跟一份指向普通目录的依赖相比，能观察到的行为没有任何差别，只是这份目录的内容认的是 tag，不是 HEAD。

checkout 换 tag——进程 pid 不变，重叠窗口不到 1 毫秒

发一次版就是在钉住的那份副本里跑 git checkout v2.0.0：四个文件（含 package.json）同时被换掉。归档的事件流里能看到从旧的开始拆到新的就绪之间有短暂重叠——1371.8ms 新的 greeter 已经进了 PENDING → LOADING，此刻旧的还没走到 1371.9ms 才发生的 DISPOSED，不是拆完了才建。

插件说过的话：[{'版本': '1.0.0', '招呼语': '早上好', '入口': '第一版'}, {'版本': '2.0.0', '招呼语': '晚上好', '入口': '第二版'}]

从旧的开始拆（1371.6ms）到新的就绪（1372.0ms），总共 0.4 毫秒；期间 timer/hmr/lab-recorder 三个条目没有一个走过 DISPOSED，换版本没有牵连别的条目。

另一个副本随便改、提交、打 tag——钉住的这份纹丝不动

pinned-d（钉住）纹丝不动

在 repo 里把三个文件全部改坏（index.js 改成语法都不完整的半成品）、提交、打新 tag v3.0.0，固定等待 15 秒——插件那边什么都没发生，钉住的那份副本连 git 状态都是干净的。

读出来的是什么

①

依赖指向一份钉在 tag 上的工作副本，插件照常加载——跟普通的 junction 没有区别，只是它认的是 tag 不是 HEAD。仓库主线已经在第二版，被钉住的这份仍然报第一版。 test_a_pinned_copy_is_just_a_dependency

②

git checkout <新 tag> 换掉插件跑的代码，进程 pid 一动不动。发一次版就是在钉住的那个副本里切一次 tag：旧的条目被拆掉（DISPOSED）、新的挂上（ACTIVE），走的是热重载那条路，不是重启；timer/hmr/lab-recorder 三个不相干的条目不受牵连。 test_b_checkout_swaps_the_version_in_place

③

拆旧、建新之间有重叠窗口，整个过程压缩在不到 1 毫秒内。本次归档的时间线：旧的 ACTIVE → UNLOADING（1371.6ms）→ 新的 PENDING → LOADING（1371.8ms，此刻旧的还没 DISPOSED）→ hmr-reload 事件（1371.9ms）→ 旧的 UNLOADING → DISPOSED（1371.9ms）→ 新的 LOADING → ACTIVE（1372.0ms），从旧的开始拆到新的就绪总共 0.4 毫秒。 test_b_checkout_swaps_the_version_in_place

④

跟着 HEAD 走的那个副本随便改、提交、打 tag，钉住的这份纹丝不动。两个工作副本各有一份文件，互不干扰——这正是「写到一半的东西不会被实例吃进去」的由来。 test_d_the_dev_copy_moves_on_alone
