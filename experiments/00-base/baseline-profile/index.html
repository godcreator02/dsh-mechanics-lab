三件套怎么长成这棵树

鼠标停在任意一个文件卡片上，右边高亮它实际造出了树上的哪个条目。 四个文件按读的顺序摆着，不是执行时序，所以这里是查关系，不是放过程。 test_baseline_profile

profile 树 · 三件套住在假 home 里的哪个位置
  • $DSH_HOME/假 home，一项一个，住 out/testhome/<项名>/
  • ├─ logs/实例的 stdout / stderr
  • └─ profiles/
  • ├─ node_modules/符号链接农场，dsh 幂等维护；timer / hmr 这些裸包名靠 Node parent-walk 在这里解析
  • └─ <名>/一个 profile（这里是 dflt 或 rooted）
  • ├─ package.jsonbundles: []，dependencies 里 base-census 走 link: 协议
  • ├─ cordis.yml恒为 []，每次启动被 profile-boot 重写
  • ├─ cordis.patch.yml活层 —— 实验改的就是这个文件
  • └─ node_modules/
  • └─ base-census →junction，指向下面那棵插件树

  • ├─ package.jsonname / type:module / exports

两个变体，唯一的差别在哪一行

基线带 hmr_root 参数，默认 []，也可以显式传 ["."]。树的形状（四个 id）在两个变体下完全一致——差别只落在 hmr 那一行 config。 test_baseline_profile

profile 树 · 当前变体落在哪个目录
  • $DSH_HOME/假 home，一项一个，住 out/testhome/<项名>/
  • ├─ logs/实例的 stdout / stderr
  • └─ profiles/
  • ├─ node_modules/符号链接农场，两个变体共用同一份
  • └─ dflt/当前变体的 profile 目录，随下方指针切换
  • ├─ package.json两个变体形状相同，只有 name 字段跟着目录名走
  • ├─ cordis.yml恒为 []
  • ├─ cordis.patch.yml两个变体唯一的差别 —— hmr 那一行 config.root
  • └─ node_modules/
  • └─ base-census →junction，两个变体各自一份
cordis.patch.yml · hmr 那一行的实际差别
  • dflt: root: []够监听 patch 文件本身，不监听代码文件
  • rooted: root: ["."]监听当前目录下的代码文件

①

树的形状完全可预测。四个 id 全是我们给的（census / hmr / include / timer），不会混进框架 fallback 那种随机 id ——对照见 framework-fallback。

②

多个 - insert: 块能在同一份活层里共存。基础设施块（timer / hmr） 与调用方块（census）各自生效，互不覆盖——两块拼接方案成立。

③

基线声明的 timer / hmr 落在 include 的子树里（⊂include）。 因为它们来自 patch 文件，整份 patch 就装在 include 的 config 里。

⚠

没覆盖到：hmr_root 确实把值写进了 config.root （源码走查成立），但本项没有单独断言去读那个值，也没验证「代码热重载真的可用」 ——这里只验证了两个变体下树的形状一致。完整证据链在 05-reload / watch-root。
