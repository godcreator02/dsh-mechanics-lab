一个实例最少需要什么

两个文件、一个空 bundle 列表，能撑起多少东西——以及哪根线剪了实例就死。

档次 ① 🔬 发现型 ✅ 5 条用例 不需要 web

一个实例是怎么拼出来的

一个 dsh 实例能跑起来，靠的是几处文件被按固定顺序拼成一棵插件树。最外层是 profile——一个目录，同时是一个 Node 包，也是一套组合配方；配方由几层 patch（补丁：对条目列表的一次编辑指令）按顺序叠加，叠出最终的 条目（entry：配方里的一行，写着挂哪个插件、给它什么配置）列表——这份 列表就是最终要跑起来的插件树。每条条目在运行时对应一个 fiber，也就是 这个插件这一次生命的载体。这一项要讲清楚的，是这整套拼装链条里最少需要哪些 零件：从几个文件，到一个真的在跑的进程。

两条硬性捆绑，怎么体现在时序上

hmr 包级声明 services.required:["timer"]——这条依赖在最小环境 里直接观测到的效果，就是下面四步。毫秒数取自 timing 这个 profile 的真实归档。

profile 树 · timing 这个 profile
  • $DSH_HOME/假 home，一项一个，住 out/testhome/<项名>/
  • ├─ logs/实例的 stdout / stderr
  • └─ profiles/
  • ├─ node_modules/符号链接农场——timer / hmr 这两个裸包名就是从这里被 Node parent-walk 解析出来的
  • └─ timing/这一节用的 profile
  • ├─ package.jsondependencies 里是 lab-recorder（link:），不是 census
  • ├─ cordis.yml恒为 []，每次启动被 profile-boot 重写
  • ├─ cordis.patch.ymltimer / hmr 两条 insert 就写在这里——下面的时间线量的就是这两条谁先谁后
  • └─ node_modules/
  • └─ lab-recorder →junction，指向 observatory/lab-recorder（不是本项 fixtures，这一节的采集器不一样）
插件树 · 本项用的教学插件
  • fixtures/base-census/包型插件：有 package.json，靠包名引用（timing 这节没用它）
  • ├─ package.jsonname / type:module / exports

捆绑体现为时序，不是「两个都在树上」那种弱判定。hmr 开始 LOADING 的那一刻 （1.4311ms）晚于 timer 到 ACTIVE 的那一刻（1.2985ms）——加载顺序由服务就位驱动， 不由 patch 里的书写顺序驱动。 test_hmr_loading_waits_for_timer_active · events-timing.jsonl

②

只差一个 timer，从活着到退出码 1。only-hmr 卡片和别的四张唯一的区别就是 没写 timer；日志判词点名 waiting for service: timer，进程当场收场， 不是「跑一会儿才垮」。 test_hmr_without_timer_wont_start
