同一个错误，两个时机，两种下场

往树上塞一个已经存在的 id——「致不致命」这个问题，得先问「什么时候」。

档次 ③ 🔬 发现型 ✅ 4 条用例 不需要 web

同一段查重代码，两处触发

EntryGroup.update() 的查重循环写在 try 块之外——两侧撞见的是同一句判词。

🧱 EntryGroup.update()
for (const options of config) {
  const id = this.tree.ensureId(options)
  if (seen.has(id)) throw new TypeError(`duplicate loader entry id: ${id}`)
  seen.add(id)
}
这个循环不管调用它的是「首次挂载」还是「热重放」——它自己不认时机

为什么下场不同：运行期撞车时，实例手上有一份挂载完好的旧树，失败的配置更新可以整体作废、退回那份旧树； boot 期第一次挂载就撞车，没有旧树可退，只能让整个 boot() 失败，进程退出。

三种撞法，撞的是同一堵墙

撞车双方来自哪一层、哪一处文件不重要——查重只看合成数组里 id 有没有重复。

①

撞车前，一个条目都没建过。查重循环在 try 块之外，抛错时 create() 一次都没调用—— 不是「挂到一半回滚」，是那次 update() 从未成功过。 静态 dump 先证明两条同 id 的条目原样进了组合数组，再验挂载期致命；witness 文件全都不存在

②

三种撞法共享同一次判定。同层两次 insert、bundle 层与活层跨层、profile 与 home 跨处—— 走的是同一段查重循环、同一句判词 duplicate loader entry id: <id>、同一个退出码 1。

③

运行期「被兜住」不是「没撞上」，是撞上了但有人接着。同样命中查重循环，但这次是热重放触发的 update()，被 refreshConfig 的 try/catch 兜着：记两条 warn、发一个 hmr/config-update-failed 事件，不回滚也不退出。 test_duplicate_id_added_while_running_is_rolled_back

④

撞完之后还得验健康，不能只看「进程没死」。一次失败的配置更新如果让代码热重载这条路悄悄坏掉， 比直接退出还糟——所以撞车之后接着改一次代码，看它还认不认。实测照样从「代码第一版」热重载到「代码第二版」。
