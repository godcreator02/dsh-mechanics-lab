04-replay / cold-surfaces

配方热重放够不到的三个面

改活层或 home 层的 cordis.patch.yml，秒级生效；同一次改动写在另外三处——组合包自己的 patch、profile 的 bundles 名单、--patch 指定的 overlay 文件——运行中的实例毫无反应，都得重启才生效。

档次 ① 📗 部分复述 + 🔬 发现型 ✅ 满覆盖 · 3 条用例 部分用例需要 web

这一项讲的是什么

dsh 支持「改配方不用重启」这条路：条目（entry，见 00-base/baseline-profile）是配方里的一行， 描述挂哪个插件、给它什么配置；profile 活层——也就是这个 profile 自己那份 cordis.patch.yml——和 home 层（$DSH_HOME/cordis.patch.yml）改了之后，靠 hmr（Hot Module Replacement，模块热替换， @deepseek-ai/cordis-plugin-hmr）的一部分机制秒级生效，这称为配方热重放。这一项要验的是： 这条热的路到底有多宽——同样是「一份决定树上有什么条目的文件」，写在另外三个位置时，运行中的实例是不是 也一样有反应。

机制怎么工作

先看四层怎么叠、哪几层被人盯着；再走一遍「文件一变会发生什么」的完整链条。

bundle 层 每个 bundles 包自带的 cordis.patch.yml 冷
profile 活层 profiles/<名>/cordis.patch.yml 热
home 层 $DSH_HOME/cordis.patch.yml 热
--patch overlay argv 传入的文件 冷

四层完整的叠加顺序与「后叠的赢」规则见 02-recipe/layer-stack——这一项只关心其中两件事： 哪几层被人盯着、bundle 层到底靠什么决定「叠不叠」。

--dump-config 是另一条完全独立的读盘路径：它背后的 composeProfile() 每次调用都现读磁盘上的 bundle 层、活层、home 层、overlay 文件，重新合成一份「配方」——这跟运行中实例内存里 那棵树是两回事，运行中实例的树只在 entry.update() 真的被调用时才变。下一节会看到这两条路径 给出完全不同的答案。

用例一时间线：bundle 层的 patch 与 bundles 名单

profile coldbundle 把 replay-cold-bundle 列进 bundles 名单——探针条目 probe 完全来自这个包自己的 cordis.patch.yml，profile 自己的活层这次没有写任何东西。 路由吐出三个指纹：moduleLoadedAt（模块几时被 import）、appliedAt（apply 几时被跑）、 configRevision（当前挂的是哪版 config）。

overlay 文件同样够不着

profile overlay-runtime 是一个最小 profile，另外用 --patch 指定一个 overlay 文件，往里 insert 见证插件（replay-cold-witness）——config 里的 value 字段就是这次要盯的东西。 见证插件把每次 apply 收到的 config 原样记进一个数组、写文件，条数本身就是「apply 被重跑过几次」的证据。

启动后见证文件1 条记录，value=initial（07:11:07.594Z）
动作把 overlay 文件里的 value 改成 changed，固定等待 10 秒（SETTLE=10.0，见 test_cold_surfaces.py）
等待后见证文件仍是 1 条记录，value 仍是 initial——没变
进程状态存活（inst.alive() 为真），没有崩溃，只是没反应

overlay 文件在 boot 时被读进内存当静态快照；热重放每次重新组合调的 composeLive() 只现读 活层与 home 层，从不重读 overlay——所以就算磁盘上的文件内容变了，运行中的实例也感觉不到。

换一条路径：活层 insert 照样热得起来

profile livepath 从没把 replay-cold-bundle 列进 bundles 名单，但它的活层直接 insert 了同一个包——id 仍叫 probe、name 仍是 replay-cold-bundle，revision 写死 live-insert。这条路径完全绕开 bundles 名单：link_plugin() 只往 node_modules 建 junction、往 package.json 的 dependencies 加一行，只关系到 Node 模块解析 （见 01-entry/name-resolution），跟「这个包是不是 bundles 名单里的一员」是完全独立的另一件事。

启动（活层 insert，不在 bundles 名单）configRevision=live-insert，moduleLoadedAt=07:11:00.367Z，appliedAt=07:11:01.001Z
重启后configRevision=live-insert（没变），moduleLoadedAt=07:11:04.582Z（换了新时刻，说明是全新进程），appliedAt=07:11:05.483Z

包在不在 bundles 名单，只决定「这个包自己那份 patch 要不要被叠进来」；活层能不能直接引用这个包的 name，是完全独立的另一件事——而且这条独立性扛得住重启，不是热重放期间暂时还没被清掉的假象。

读出来的是什么

①

bundle 层的 patch 文件、profile 的 bundles 名单、--patch overlay 文件——三样都是冷的。 watchUserPatches() 只给活层和 home 层各注册了一个 hmr.registerConfig() 回调，除此之外 没有任何代码在监听文件系统；这三处都不在那两个注册目标里，改了必须重启才生效。 test_bundle_patch_and_bundles_list_are_cold · test_overlay_file_is_cold

②

包在不在 bundles 名单、活层能不能直接引用它，是两条互不相干的注册路径。包从名单摘掉不影响活层 insert 同一个包照常挂上，且这条独立性在重启后依然成立。 test_two_registration_paths_are_independent

③

--dump-config 是个陷阱：它是纯读盘的静态合成，改完 bundle 层的 patch 立刻能读到新值， 但那跟「运行中实例有没有反应」是两回事，不能拿它当「进程内状态变了」的证据。 test_bundle_patch_and_bundles_list_are_cold

④

三处冷面不是「故意不响应」，是压根没人往那个方向看一眼。热重放每次重新组合调的 composeLive()，只现读 profile 活层与 home 层；bundle 层的 patch 与 --patch overlay 都是 boot 时读进内存的静态快照，重放时用的还是那份内存数据，不重读磁盘。 test_bundle_patch_and_bundles_list_are_cold · test_overlay_file_is_cold

判定与证据出处在 test_cold_surfaces.py 的模块 docstring，此页只负责让你看懂。

/**
 * replay-cold-bundle —— 身兼两职：
 *
 *   1. **组合包**（profile bundle）：`package.json` 声明 `dsh.bundle.patch`，
 *      指向同目录的 `cordis.patch.yml`。列进某个 profile 的
 *      `dsh.profile.bundles` 之后，这份 patch 就是它对配方的贡献——跟官方
 *      publish.md 的 hello-plugin 一模一样的写法：一个包，patch 里的条目
 *      按包名引用自己。
 *   2. **它自己 patch 里指向的那个插件模块**：真正的 `apply` 就长在这个文件里。
 *
 * 探针路由把三个指纹吐出来，让测试从进程外部分辨「模块有没有被重新
 * import」和「这次挂着的是哪一版 config」：
 *
 *   marker          代码版本指纹，写死在源码里，除非改代码否则永远不变
 *   moduleLoadedAt  模块被 import 的那一刻（模块级常量）——只有重新 import
 *                   （整进程重启，或代码热重载）才会变
 *   appliedAt       这次 apply 被调用的那一刻——只要 apply 被重跑就会变，
 *                   不需要重新 import 也能变（比如活层热重放只改 config 时）
 *   configRevision  回显 config.revision——当前挂着的是哪一版 config
 */

export const inject = ["webServer"];

const MARKER = "replay-cold-bundle-v1";

/** 模块被 import 的时刻，模块级、只赋值一次。 */
const MODULE_LOADED_AT = new Date().toISOString();

export function apply(ctx, config) {
  const appliedAt = new Date().toISOString();
  const route = config?.route ?? "/replay-cold-bundle/state";
  const revision = config?.revision ?? null;

  // 路由必须用 ctx.effect 包住：不包的话插件卸载后路由会泄漏、继续应答。
  ctx.effect(
    () =>
      ctx.webServer.register({
        kind: "exact",
        path: route,
        handler: (req, res) => {
          if (req.method !== "GET" && req.method !== "HEAD") {
            res.writeHead(405);
            res.end();
            return;
          }
          res.writeHead(200, {
            "content-type": "application/json; charset=utf-8",
            "cache-control": "no-cache",
          });
          res.end(
            JSON.stringify({
              marker: MARKER,
              moduleLoadedAt: MODULE_LOADED_AT,
              appliedAt,
              configRevision: revision,
            }),
          );
        },
      }),
    "replay-cold-bundle: state route",
  );
}

/**
 * 见证员：把每次 apply 收到的 config 原样记下来。
 *
 * 只关心一件事——「这个条目的 config 有没有变」。用途是验证「运行期改
 * `--patch` 指向的文件，实例会不会把新内容读进来」：如果不会，见证文件应当
 * 永远只有一条记录，且 `value` 字段停在启动时的初始值。
 *
 * 记录数组建在模块级，写文件时写整个数组——万一这个条目真被重挂了，重挂本身
 * 也该在见证文件里留痕，而不是被覆盖掉、变得跟「只 apply 过一次」一模一样。
 */
import { writeFileSync } from "node:fs";

const MARKER = "replay-cold-witness-v1";
const records = [];

export function apply(ctx, config) {
  const out = config?.out;
  if (!out) throw new Error("replay-cold-witness: config.out 是必需的");

  records.push({
    marker: MARKER,
    applyIndex: records.length,
    at: new Date().toISOString(),
    value: config?.value ?? null,
  });
  writeFileSync(out, JSON.stringify(records, null, 2), "utf8");
}
