05-reload / ignore-rules

同一份代码，为什么有时候不热重载

hmr 主 watcher 判断要不要重载一份代码，要闯两道关卡：ignored 名单先筛一遍「看不看得见」，loadCache 的字符串判等再筛一遍「算不算数」——这一项把两道关卡分别钉死，钉的是经 junction 装进来的代码。

档次 ① 🔬 发现型 ✅ 满覆盖 · 5 条用例 不需要 web

这一项讲的是什么

条目（entry，见 00-base/minimal-profile）在运行时对应一个 fiber——插件这一次生命的载体。给一条条目挂 @deepseek-ai/cordis-plugin-hmr（provide 一个叫 hmr 的服务，包级硬依赖 timer）之后，它会拿 root 配置里列出的目录去监视文件变化：改一处代码，hmr 把对应插件的 fiber 拆了重建，条目本身的 id 不变——这段「拆旧建新」的时序 05-reload/watch-root 已经画过，也讲过 root 该怎么填才能覆盖到代码所在的目录。

真实的插件代码往往不是物理放在 profile 目录里面，而是作为一个 npm 依赖被 link: 进来——生产环境靠 pnpm 的 hoisted linker，这套实验台靠 mklink /J，两者落地的都是同一种东西：junction，Windows 上的目录重解析点，效果类似符号链接，不需要管理员权限。profile/node_modules/<包名> 是一条 junction，真正指向别处的一个目录。

这一项要钉死的是：同一份代码，只换一条告诉 hmr 的路径——是这条 junction 本身、还是它指向的真实目录——热重载发生与否就跟着变，原因分两层：一层是 watcher 从没见到这个改动（挡在 ignored 筛子上）；另一层是 watcher 见到了，代码热重载依然没有发生（它报出的路径和 loader 记的路径不是同一个字符串）。

机制怎么工作

下面走一遍改一处代码之后，这条变化要闯的两道关卡：①②③是 chokidar（Node 生态最常用的文件监听库）那道 ignored 筛子怎么判「看不看得见」，④⑤是看见之后，hmr 拿这条变化去跟 loader 的 loadCache 对账，判「算不算数」。

ignored 默认值['**/node_modules', '**/.*', 'cache', 'data']
本项改过这份名单的用例nodot（去掉 **/.*）

五个 profile，同一份代码换着法子接进来

五个 profile 都 link 了同一份教学插件（fixtures/hmr-linked，侧栏可点开），它的 apply() 只做四件事：报代码里写死的版本号、报 config 里的版本号、报自己的模块 URL 与 loadCache 里跟自己有关的 key、报载入次数。用例把 index.js 里的「第一版」改成「第二版」——版本号变没变，就是判断有没有重载的信号。五个 profile 只有 root、ignored、还有源码物理放哪儿不一样。

读出来的是什么

①

挡住经 junction 装进来的代码热重载的，是 watcher 的 ignored 名单，而且是被 **/.* 误伤的。hmr 筛的是相对 watch base 的路径，watch base 之外的路径以 .. 开头；Windows 上这串反斜杠路径被 picomatch 当成一整段，一段以点开头就撞上了默认名单里「忽略隐藏文件」那条。 test_watching_the_real_source_dir_is_silently_ignored

②

这条误伤只在源码位于 watch base 外面时发作，不是「junction 形态跟 hmr 不兼容」。把 **/.* 拿掉，同样的配置立刻就通——配置只差这一项，结果从「一声不出」翻成「重载成功」。 test_dropping_the_dotfile_rule_makes_it_work

③

躲过筛子不等于会重载：watcher 报出的路径从不做 realpath，loadCache 的 key 永远是 realpath，两者不是同一个字符串。root 直接填 junction 路径本身时，chokidar 确实报了变化（hmr-change），但 Map.has() 判等失败，代码热重载没有发生。 test_watching_the_junction_path

④

这条规律不分「你手填链接路径」还是「chokidar 自己爬进去」。profile 里建一条 junction 指向外部源码、hmr 全默认配置，chokidar 确实跟着 followSymlinks 爬了进去、报了变化，但报的还是链接路径，同样对不上 loadCache。 test_junction_inside_profile_pointing_out

⑤

把源码搬进 profile 目录，两条规则都不用改。相对路径不再以 .. 开头（躲开隐藏文件规则），也不含 node_modules 一段——默认配置直接热重载。 test_source_nested_under_profile_needs_no_hmr_change

五条用例共同钉死一个充要条件：watcher 报出的路径经 pathToFileURL 之后要跟 loadCache 的 key 字节相同，watch 的入口必须本身就是真实路径——不是「junction 不行」，是「junction 报的字符串对不上」。

⚠️ root／ignored 两个键要「一起动」这件事，本项只验了一个方向——只扩 root 不改 ignored（上表 source 那行：watcher 一声不出）。另外两个方向——只清空 ignored（不只是去掉 **/.* 那一条）、只改 ignored 不扩 root——目前只有源码依据，没有用例覆盖，本项不展开。

判定与证据出处在 test_ignore_rules.py 的模块 docstring，此页只负责让你看懂。

/**
 * 教学插件——一个包，声明了 `dsh.bundle`，但那一段只在包名进了 profile 的
 * `bundles` 名单时才生效，没进名单它就是个普通依赖。两种形态用同一个包。
 *
 * 它干四件事：
 *
 *   1. 报自己代码里写着的「版本」。这三个字就是它的代码，用例把「第一版」
 *      改成「第二版」——于是它再跑一次时说的话不一样，一眼分得出重来过没有。
 *   2. 报 `config` 里那个「版本」。跟上一条来路不同：那个改代码、这个改配方。
 *   3. 报身份三件套：模块 URL、树的 baseUrl、loadCache 里跟自己有关的 key。
 *      「junction 那头的代码算不算 node_modules 里的东西」，答案就藏在第一个里。
 *   4. 报载入次数（模块顶层的计数器）和 `compute()` 的结果。
 */

import { compute } from "./helper.js";

let loads = 0;

export const inject = ["labObserver"];

export function apply(ctx, config) {
  const say = ctx.labObserver.for(ctx);
  loads += 1;

  say("我跑起来了", {
    版本: "第一版",
    配置版本: config?.版本 ?? null,
    载入次数: loads,
    算出来: compute(),
  });

  // 我自己是从哪个 URL 被加载的。经 junction 装进来的包，这里报出的是链接
  // 路径还是链接那头的真实路径，直接决定 hmr 那三处
  // `url.includes('/node_modules/')` 命不命中。
  say("我的模块 URL", { url: import.meta.url });

  // hmr 的 baseDir 由 `config.base || '.'` 相对它解析，root 又相对 baseDir。
  say("树的 baseUrl", { baseUrl: ctx.baseUrl ?? null });

  const loader = ctx.get("loader");
  const cache = loader?.internal?.loadCache;
  if (!cache) {
    say("loadCache", { 拿到了: false, 说明: "loader.internal 不在（没开 --expose-internals？）" });
  } else {
    const mine = [];
    for (const key of cache.keys()) {
      if (String(key).includes("hmr-linked")) mine.push(String(key));
    }
    say("loadCache 里跟我有关的 key", { 条数: mine.length, keys: mine });
  }
}
