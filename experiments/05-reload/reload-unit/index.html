05-reload / reload-unit

重载的单位是插件入口

hmr 判定一处代码改动要走「代码热重载」这条分支之后，重来的范围只认一件事——这份代码属于哪个插件入口，不管它内部拆成几个文件、被几个条目各挂一份，一起重来的都是这个入口文件本身。

档次 ① 🔬 发现型 ✅ 满覆盖 · 2 条用例 不需要 web

这一项讲的是什么

条目（entry，配方里的一行，见 00-base/minimal-profile）运行时对应一个 fiber——这个插件这一次生命的载体，滑过 PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED 这几个状态（完整定义同见 00-base/minimal-profile）。hmr（@deepseek-ai/cordis-plugin-hmr 提供的服务）在它监视的目录树里看到一处代码改动、且判定这处改动要走「代码热重载」这条分支后（监视范围由 root 配置决定，完整语义见 05-reload/watch-root），会把相关的插件代码重新 import 一遍：旧 fiber 走一遍 dispose，新的重新 apply，运行中的实例不用重启进程就吃到新代码。

这一项要讲清楚的是「相关的插件代码」到底圈到哪儿——同一份代码可能被拆成好几个文件，也可能被两个不同的条目各挂一份，改一处代码之后重来的到底是哪个范围、殃及几个条目、发几次重载事件，这几件事分得很开，答案也不直观。

机制怎么工作

走一遍 hmr 服务里 partialReload()（@deepseek-ai/cordis-plugin-hmr 的 src/index.ts）判定要重来哪些插件、怎么重来的过程：①②收集并解析出入口，③判定谁被这次改动沾上，④原子重来，⑤把所有相关 fiber 逐个重挂。

改一次代码，两条都重来

twoids profile（侧栏可点开）把 hmr-linked 这个包挂了两次，来路不同——bundle 层（包自己带的 patch，包名进了 profile 的 dsh.profile.bundles 名单后自动生效）与活层（profile 自己的 cordis.patch.yml 手写的一条），两者的完整语义见 02-recipe/insert-semantics。greeter 是 bundle 层贡献的那条（fixtures/hmr-linked/cordis.patch.yml 里写死的 id），greeter-live 是活层另外手写的一条不同 id 的 insert，config.版本 写成「活层这条」。两个条目用的是同一份代码，代码以 bundle 形式挂在 profile 外面，所以 hmr 的 root 除了 '.' 还额外加了这份代码的真实路径（watch="source"）——root 各种取值的完整对照见 05-reload/watch-root。

「载入次数」是 index.js 模块顶层的计数器（let loads = 0，侧栏可查看），不是 fiber 的状态——两次都数到 1、2 这同一组值：greeter 的 apply 先跑（数到 1），greeter-live 的 apply 后跑（数到 2）。改代码之后这组数字原样重演，说明两个条目共享的是同一次 import 出来的同一个模块实例——模块被整个重新求值、计数器归零重数，不是各自独立重载出两份模块。

cordis 发出的事件本身叫 hmr/reload（ctx.emit('hmr/reload', reloads)，reloads 是一个 Map<Plugin, Reload>）；lab-recorder 采集后把它记成 kind: "hmr-reload"，count 字段就是这个 Map 的大小——按 Plugin 去重的重载条数，不是按 fiber 数、也不是按文件数。这次改动只让一个 Plugin 进了这个 Map（greeter 和 greeter-live 解析到的是同一个模块），所以：

hmr-reload 事件的 count1
hmr-reload 事件的 files[".../src-twoids/hmr-linked/index.js"]（唯一一条）
greeter 的状态序列里 ACTIVE 出现次数2
greeter-live 的状态序列里 ACTIVE 出现次数2
旧的 ACTIVE→UNLOADING 到两条都回到 ACTIVE约 0.65ms（1336.66ms → 1337.31ms）

改一个纯函数辅助文件，重来的仍是整个入口

helper profile（侧栏可点开）只挂了一次 greeter，代码这次挪进了 profile 目录里面（源码目录在 profile 内部，hmr 的 root 只写 ['.'] 就够——完整语义同见 05-reload/watch-root）。用例只改 helper.js 里那个不碰 ctx 的纯函数 compute()，index.js 一个字节都不动。

用例耗时2.52s（summary.md）

两处证据缺一不可：「算出来」变成了新值，说明 helper.js 里的新实现确实生效了（没有被缓存挡住）；hmr-reload 报的文件名却是 index.js，不是被改的 helper.js——重来的单位是入口，不是被改的那个文件本身。

读出来的是什么

①

重载的单位是插件，不是条目。同一份代码被两个不同 id 的条目各挂一份，改一次只触发一次 hmr/reload，但两个 fiber 全部重挂——重挂遍历的是 runtime.fibers，一个 Plugin 的所有 fiber，各自沿用自己的 oldFiber._config。 test_both_layers_different_ids_both_reload

②

拆文件缩不小重载范围。改一个只有纯函数、从不碰 ctx 的辅助文件，hmr/reload 报出来的文件仍是插件入口 index.js——把逻辑拆出去以为能单独热替换的想法不成立，付出的代价跟改主文件一样。 test_editing_an_imported_helper_reloads_the_whole_plugin

/**
 * 纯算法文件。它不导出插件、不碰 ctx、不注册任何东西——只是被 index.js
 * `import` 进去的一个函数。
 *
 * 这一项改的就是这个文件，一个字都不碰 index.js：看重来的是这个文件，
 * 还是整个插件入口。
 */

export function compute() {
  return "算法第一版";
}

/**
 * 教学插件——一个包，声明了 `dsh.bundle`，但那一段只在包名进了 profile 的
 * `bundles` 名单时才生效，没进名单它就是个普通依赖。
 *
 * 它干四件事：
 *
 *   1. 报自己代码里写着的「版本」。用例把「第一版」改成「第二版」，一眼分得出
 *      重来过没有。
 *   2. 报 `config` 里那个「版本」——来路不同：那个改代码、这个改配方。
 *   3. 报身份三件套：模块 URL、树的 baseUrl、loadCache 里跟自己有关的 key。
 *   4. 报载入次数（模块顶层的计数器）和 `compute()` 的结果。
 */

import { compute } from "./helper.js";

/**
 * ⚠️ 模块顶层的状态，不是 fiber 的状态。热重载会把整个模块重新求值一遍，
 * 这一行也会重跑——于是它归零；同一个模块被两个条目挂着时，两次 apply
 * 共享同一个模块实例，这个数会数到 2。同一个计数器，两种现象分得开。
 */
let loads = 0;

export const inject = ["labObserver"];

export function apply(ctx, config) {
  const say = ctx.labObserver.for(ctx);
  loads += 1;

  say("我跑起来了", {
    版本: "第一版",
    配置版本: config?.版本 ?? null,
    载入次数: loads,
    算出来: compute(),
  });

  say("我的模块 URL", { url: import.meta.url });
  say("树的 baseUrl", { baseUrl: ctx.baseUrl ?? null });
}
