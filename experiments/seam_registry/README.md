# seam · 想让多个实现并存，那就别让它们争名字

```powershell
uv run pytest experiments/seam_registry/ -n 0 -s
```

3 个用例 / 约 11 秒 / 不需要 web ｜ 🔬 发现型

## 这一项讲什么

上一项立住了铁律：一个名字只有一个主人，第二个来占的当场失败。

想让多个实现并存，办法不是打破那条铁律，是**绕开**它：只让一个插件占名字
（名册），别人往它肚子里的表塞。从头到尾没人跟谁争。

装置：名册（占 `labRoster`）＋ 若干注册方（`inject` 名册、往表里塞一行）＋
一个使用方（`inject` 名册、每 300ms 把表内容报进事件流）。

## 实测判定

### 一、两个注册方并存，谁也不撞谁

对照上一项：那边两个插件抢同一个名字，一个当场失败、整个实例陪葬；这边两个插件
往同一张表里塞，两个都跑到 `ACTIVE`，表里两行。

### 二、表是空的，使用方照样活

把注册方全撤掉，只剩名册和使用方：使用方走 `LOADING → ACTIVE`，拿到一张空表，
实例照常活着。

**这是注册表式跟独占式最要紧的一处分别。** 独占式的提供方缺席等于名字没人占，
使用方 `inject` 不到就停在 PENDING、启动期还会拖垮整个实例；这边名字有人占着
（名册自己），空表不构成任何错误——失败推迟到真正去用表里的东西那一刻。

### 三、注册方下线，只少它那一行

实例跑着的时候把「贡献乙」禁用掉（活层热重放），观测到：

| 谁 | 变化 |
|---|---|
| 表内容 | `['贡献乙','贡献甲']` → `['贡献甲']` |
| 贡献乙 | `LOADING → ACTIVE → UNLOADING → DISPOSED` |
| 名册 | 状态序列**一个字没多** |
| 使用方 | 状态序列**一个字没多** |

表项的寿命跟着**塞它的那个插件**走，不跟着名册走。这靠的是上一项测出来的那条：
名册的 `register()` 里那句 `this.ctx.effect(...)`，`this.ctx` 属于调用方，
所以 effect 挂在注册方的 fiber 上。

## 观测手法

「表里有什么」这个信号由使用方自己每 300ms 报一次，进的是跟框架事件同一条时间轴。
好处是热重放前后的表内容变化直接读得出来，不用去猜哪一刻该采样。

判定三同时验两件事，用的手段不同：**该变的**（表少一行）用轮询等，**不该变的**
（名册与使用方的状态序列）用改动前后两次快照对比。
