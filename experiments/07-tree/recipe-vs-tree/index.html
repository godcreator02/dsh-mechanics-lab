配方 ≠ 运行时的树

--dump-config 算出来的东西，和进程里真正跑着的那棵树，差一个条目。

档次 ②🔬 发现型 ✅ 1 条用例不需要 web

你写了三条，树上有四个

左边是 patch 文件写的，右边是普查员在进程里数出来的。 指任意一条，另一侧会点出它的对应物——只有 include 指不到。

配方（--dump-config）

- insert:
  - id: timer
  - id: hmr
  - id: census
↑ 这里翻遍了也没有 include
→

运行时的树

include 配方里没有
timer
hmr
census
include 这个条目
config.patches ＝ 整份配方：
  timer · hmr · census
↑ 这份清单里没有 include 自己

整份 effective config 就装在它自己的 config 里——
它要是出现在其中，就是自指。所以不管配方怎么写，dump 都看不见它。

← → 键也行
①

树比配方多的，只有 include 一个。反过来那半也成立——配方里写的每一条都真的上了树， 没有「算出来了却没挂上」的漏网条目。 test_include_is_the_only_ghost · 实测四个条目，parent 全指向 include

②

热重放就是改 include 这一个条目的 config。配方既然整份装在它里面， 「重新 compose 一遍配方」在实现上就等于给它换一个 config—— 这条是 04-replay 那一组的地基。

⚠

幽灵条目的 id 每次启动都不一样，只能认 name 不能认 id。 写断言时的硬约束——本项的基线显式声明了 timer/hmr 才让树形可预测， include 是唯一例外（id 是固定字面量）。

判定与证据出处在 test_recipe_vs_tree.py 的模块 docstring，此页只负责让你看懂。
