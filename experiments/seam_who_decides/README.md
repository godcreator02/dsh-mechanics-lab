# seam · 使用方能不能跑起来，谁说了算

```powershell
uv run pytest experiments/seam_who_decides/ -n 0 -s
```

3 个用例 / 约 9 秒 / 不需要 web ｜ 🔬 发现型

## 这一项讲什么

前三项读下来容易得出一个印象：独占式的提供方缺席，使用方卡住、整个实例陪葬；
注册表式的表空着，使用方照样活。好像命运由「怎么安排多个实现」决定。

这一项拆穿它。三个用例共用同一个使用方文件、一个字都不改，换的只是对面那份名册；
而两份名册之间只差一个方法：

```js
[Service.check]() { return this.表.size > 0 }
```

框架在决定「等着这个服务的插件能不能开跑」之前会问一次，答否就当它不在。

## 实测判定

### 一、判据说了算，不是安排方式说了算

| 名册 | 表 | 使用方 | 实例 |
|---|---|---|---|
| 严格版（有判据） | 空 | 卡在 PENDING，`apply` 一次没跑 | **起不来，退出码 1** |
| 严格版（有判据） | 有一行 | `LOADING → ACTIVE` | 活 |
| 宽松版（无判据） | 空 | `LOADING → ACTIVE`，拿到空表 | 活 |

第一行和第三行的表同样是空的，使用方同样一个字没改——差别只在名册那边多写/少写
一个方法。**「独占还是注册表」不决定使用方的命运，那一刻的可用性判据才决定。**

第一行里名册自己是 `ACTIVE` 的：卡住使用方的不是「名册没起来」。

### 二、判据否决造成的 PENDING，日志报不出在等谁

这是本项最该记住的一条。两种 PENDING 的判词不一样，而且是往难查的方向不一样：

| 情形 | 判词 |
|---|---|
| 压根没人提供这个名字 | `pending (waiting for service: labSomething)` — **点得出名字** |
| 有人占着，判据说不可用 | `pending (waiting for services: unknown)` — **点不出名字** |

名字确实被占着，启动期审计那一侧看不出缺的是谁，只能报 `unknown`。所以看到
`waiting for services: unknown` 时，方向不是「去找谁没提供这个服务」，而是
「去找哪个服务的可用性判据正在返回否」。

判词前半截是条目的 `name`（`./roster-user.mjs`）而不是它的 id，排错时按 `name`
去 patch 文件里找那一行。

## 本项的范围

只测了**静态**场景：名册开张时表里有没有东西，判据在那一刻给什么答案。
「表在运行期从空变成非空，等着的插件会不会被唤醒」不在本项装置的覆盖范围内。
