四层怎么叠出生效配置

profile 真正跑起来的配置，由四份 patch 文件按固定顺序层叠而成——同一个 id 在多层各写一次，后叠的赢。

档次 ① 📗 复述型 ✅ 8 条用例 不需要 web

这一项讲的是什么

profile（见 00-base/minimal-profile）真正跑起来时用的那份配置——插件系统内部管它叫组合树（composed tree）——不是直接写在某一个文件里的，是启动那一刻现算出来的。算法是层叠：从一个空数组开始，按固定顺序把几份 patch 文件的内容依次叠上去。patch 是对条目（entry，见 00-base/minimal-profile）列表的一次编辑指令——不是一份完整的配置，是「往列表里插一条」或「把某个 id 的内容换掉」这类指令的集合，后面会看到具体写法。这一项讲的正是这套层叠机制本身——一共叠几层、每层的文件在哪、谁写的、层与层之间谁压过谁。

机制怎么工作

生效配置在空根之上按固定顺序逐层组合，走一遍这四层——①②③是三份各自独立的文件，④是命令行临时指定的第四份。

四层叠加时有个共同规矩：后应用的层按 id 覆盖前面各层同 id 的那一行，而且是把目标行的 config 整个换掉，不是按键合并——docs/official/zh/user/develop/basic/publish.md:123 原话：「后应用的层按行胜出，且 patch 会替换目标行的整个 config 值，而不是深度合并各键。」后面「同一个 id 叠四次」那组观测能直接看到这条规矩的效果：某一层只要重述了 config，前一层写在同一个 config 里、没被重述的键会跟着消失。

怎么测：静态 dump 就是四层叠加的直接产物

四层怎么叠是配方层面的事——dsh --dump-config 把组合结果打印出来，秒级返回，不用真的拉起一个实例，比起一个真进程便宜得多。本项 8 条用例里只有 3 类必须真的拉进程：home 层文件缺失时要确认「进程真的能启动、能活着」（dump 不报错只能证明静态组合没崩，证明不了这件事）；home 层对整个 home 生效的那三条用例，判据是条目自己报出来的 config 内容，不是 dump 能替代的。

四层各自的来源，dump 报得出来

identify profile（侧栏可点开）叠了 l04-bundle-a 这个教学组合包，四层各插一条互不重名的标记条目——from-profile 写在 profile 活层，from-home 写在 home 层，from-overlay 由 --patch overlay-identify.yml 传入。--dump-config 对每条都标出它是从哪一层来的。

组合树条目总数6 个：from-bundle / shared / order-test / from-profile / from-home / from-overlay
from-bundle 来源l04-bundle-a（包名）
from-profile 来源D:\…\layer-stack\profiles\identify\cordis.patch.yml
from-home 来源D:\…\layer-stack\cordis.patch.yml（home 层）
from-overlay 来源D:\…\layer-stack\overlay-identify.yml

bundle 层的来源标的是贡献这条 patch 的包名；profile 活层、home 层、overlay 三层的来源标的都是那份文件本身的绝对路径——四种来源在同一次 dump 里并存，「这条是从哪一层来的」从不用猜。

同一个 id 叠四次，一路跟着变

precedence profile（侧栏可点开）里，shared 这个 id 在四层各出现一次：bundle 层的 l04-bundle-a 用 insert 建出它（config: {layer: bundle, seq: 1}），profile / home / overlay 三层各用裸 - id: shared 覆盖它一次。每加一层重新 dump 一次，不只看终点：

只有 bundle 层shared.config = {'layer': 'bundle', 'seq': 1}
叠上 profile 层后shared.config = {'layer': 'profile'}
再叠上 home 层后shared.config = {'layer': 'home'}
最后叠上 overlay 层shared.config = {'layer': 'overlay'}

注意 seq: 1 这个键——bundle 层写了它，profile 层覆盖 shared 时只重述了 layer，没有重述 seq，叠上去之后 seq 就跟着消失了。这正是上一节「整层替换、不按键合并」那条规矩的直接后果，不是巧合。

home 层：文件缺失 vs 内容非法

home 层是可选的一层，但「可选」只体现在「文件不存在」上；文件存在但写错格式是另一种命运。两条用例各自用了一个独立的 profile（侧栏可点开 missing-home / illegal-home 的活层——都是空 []，实验对象在 home 层，不在这份文件）。

missing-home✓ 正常启动
home 层文件不存在

报错文本固定，出自源码 JSDoc（这次归档里的调用栈显示 dsh-app-boot/lib/index.js:840 一带），不是文档正文——引用时不能写成「文档说」；行号会随打包版本变，判定依据的是报错文本不是行号。

--patch 可以给多个，按 argv 顺序

第四层本身还能再叠：overlay-order profile 的活层是空的，靶子是 bundle 层建出来的 order-test 条目，两份 overlay 文件各用裸 id 改它的 which 字段，交换两次调用的顺序。

--patch a b
order-test.config.which = 'b'
后写的 b 胜出
--patch b a
order-test.config.which = 'a'
后写的 a 胜出

跟前三层是同一条「后叠的赢」的规矩，只是这次发生在第四层内部。⚠️ 运行期改一份已经生效的 --patch overlay 文件，热重放拾不拾得到——这条判定归 04-replay/cold-surfaces，本项不重复验证。

home 层不属于任何一个 profile

home 层还有一条前三层都没有的性质：它不挂在任何一个 profile 名下，写一次，这个 home 下每个 profile 启动时都会读到。三条用例都真的拉起了实例——判据是条目自己报出来的 config，不是 dump。home-side 的活层（侧栏可点开）只有基础设施，一个字都没提 in-home；twin-a / twin-b 是两个各自独立的 profile；both-sides 的活层自己写了一条 in-profile。

home-side · in-home 收到的 config{"出处": "home 层"}
twin-a · in-home 收到的 config{"出处": "home 层"}
twin-b · in-home 收到的 config{"出处": "home 层"}
both-sides · in-profile 收到的 config{"出处": "profile 层"}
both-sides · in-home 收到的 config{"出处": "home 层"}

home 层写一次，twin-a 和 twin-b 两个独立实例都收到同一份 in-home；both-sides 里 profile 层写的 in-profile 不会因为 home 层也写了东西就消失——两层是拼在一起的，不是二选一。

读出来的是什么

①

四层顺序：bundle → profile 活层 → home 层 → --patch overlay，逐层组合在空根之上，同一个 id 一层比一层新。 test_four_layers_identifiable · test_same_id_layers_precedence

②

home 层文件不存在，等价于「没有这层」，正常启动。 test_home_layer_missing_equals_no_layer

③

home 层内容非法（顶层不是数组）必须 fail loud，报错文本固定。出处是源码 JSDoc，不是文档正文。 test_home_layer_illegal_content_fails_loud

④

--patch 给多个时也按「后来者赢」——argv 顺序，后写的顶掉先写的。跟前三层是同一条规则，只是发生在第四层内部。 test_overlay_order_by_argv

⑤

home 层不属于任何一个 profile：写一次，这个 home 下每个 profile 都吃到；跟 profile 层各写各的也不冲突，两条并存、各收各的 config。 test_the_other_place_works_the_same · test_the_home_place_hits_every_profile · test_two_places_two_entries

⚠

矫正点：官方文档说的「四层」，源码层面实际是五层。框架自己在 --patch overlay 之后还追加了一层内置补丁，只受「组合树里有没有对应 id」和环境变量驱动，压过前四层——但本项零用例覆盖它，标 ⚠️ 待验，不进上面的判定。源码坐实：dsh 包的 composeProfile() 里，最终 overlay 列表是先复制一份 argv --patch 列表，再在后面追加两条框架内置补丁（agent-presets 根路径合并、session-telemetry-otel 的禁用开关），各有前置条件，细节见 test_layer_stack.py docstring 的「没覆盖到的」一节。

判定与证据出处在 test_layer_stack.py 的模块 docstring，此页只负责让你看懂。

/**
 * 把自己收到的 config 原样报给 lab-recorder。
 *
 * 用于「同一个条目在 profile 层与 home 层都被写到时，它最后收到的是哪一份」
 * 这类判定——判据只能是插件自己报出来的内容，写进哪个文件是我们做的事，
 * 收到什么是它说的事，两边摆在一起才叫对上了。
 */

export const inject = ["labObserver"];

export function apply(ctx, config) {
  const say = ctx.labObserver.for(ctx);

  say("我收到的 config", { 类型: typeof config, 内容: config ?? null });
}
