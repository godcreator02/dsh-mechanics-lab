02-recipe / insert-semantics

insert 是新增条目的唯一姿势

patch 对条目列表能做的编辑只有三种形态；这一项只讲能真正新增条目的那一种——- insert:。不带 id 和带 id 是两套完全不同的语义，认错了目标，插入会被整条跳过而不报错。

档次 ① ⚠️ 矫正型 ✅ 满覆盖 · 3 条用例 不需要 web

这一项讲的是什么

条目（entry，见 00-base/minimal-profile）是配方里的一行。整棵组合树 100% 由 patch——对条目列表的一次编辑指令——叠出来，根永远是空数组。patch 有三种形态：不带 id 的 - insert:、带 id 的 - insert:、以及 - id: X 直接定位已有条目改字段。前两种都用 insert 关键字，但落地位置完全不同；第三种根本不新增条目，只改已有条目的字段。这一项讲的正是前两种——insert 到底往哪儿插，插不进去时框架怎么应对，以及插进去的条目在组合树里怎样被标出它的来路。

机制怎么工作

走一遍 applyEntryPatches()（cordis-plugin-include）处理一条 patch 项时的分支：①②是 insert 落地位置的两条路，③是②那条路上的校验失败分支，④是插入之后组合树记账的方式。

怎么测：静态 dump 就是真组合树

dsh --dump-config 的 renderConfigDump() 与运行时挂载的 Include.applyPatches() 走的是同一个 applyEntryPatches() 调用，所以本项全部用例只用静态 --dump-config，不用拉真实例——算出来的树和真实挂载走的是同一套 compose 逻辑，不是近似。insert 的警告走 stderr、不进 stdout、也不改变退出码；lab.dump_config() 成功时会把 stderr 静默丢弃，本项自己包了一层 dump_with_warnings() 才能把警告带出来判定。

不带 id：两条原样进了根组

insert-root profile（bundles: []，侧栏可点开）的活层只写了一条 patch 项——只有 insert 字段，没有顶层 id。insert 列表里两条各自带的 id: alpha / id: beta 是新条目自己的树内地址，跟这条 patch 项顶层有没有 id 是两件事。

insert-root✓ 原样追加
patch 项 = 一条 insert，不带顶层 id
组合树 id 列表 = ['alpha', 'beta']（0.56s）
stderr = （空）——完全合法，没有任何警告
insert-nongroup⚠ 警告并跳过
patch 项 = 两条：先不带 id 的 insert 建出 leaf，再一条顶层 id: leaf 附带 insert 想往 leaf 里塞 child
组合树 id 列表 = ['leaf']（0.54s）——没有 child
leaf.config = {"x": 1}，原封不动
patch insert: entry "leaf" is not a group

第二个 patch 项的顶层 id: leaf 指向的是已存在的 leaf 条目，想把它当 group（标记 group: true 的条目，它的 config 字段本身就是子条目数组）塞孩子进去。但 leaf 本身只是普通条目，没有 group: true——applyEntryPatches() 只在 stderr 打上面那一行警告，整条 patch 项被跳过：child 一个都没被创建，leaf 自己的字段也毫发无损，不是报错中断整个 dump。

来源写在脸上：活层 insert 出来的条目

insert-lands profile 的 bundles 里带了 @deepseek-ai/dsh-base，活层用不带 id 的 insert 挂了一条真的教学插件 lab-minimal（fixtures/lab-minimal，link 进这个 profile，侧栏可查看它的 apply()）。dump 对每个条目都标出它是从哪一层来的——两种层两种形式，从不用猜。

活层条目的来源是那份 cordis.patch.yml 文件本身的绝对路径；bundle 层条目的来源是贡献这条 patch 的包名。同一次 dump_config() 里两种来源并存，读者不用去猜「这条是谁塞进来的」。

读出来的是什么

①

不带 id 的 - insert:，insert 列表原样追加进根组。官方文档展示过这种写法，但没有明确说「追加进根组」这句话本身——这条从源码坐实。 test_insert_without_id_appends_to_root

②

矫正点：带 id 的 - insert:，那个 id 指的是已存在的目标 group，不是给新条目起名字。目标存在但不是 group 时只警告、整条 patch 被跳过——子条目一个都不会创建，目标条目本身也毫发无损，不是报错中断。官方文档完全没提这条语义。 test_insert_with_id_targeting_non_group_warns_and_skips

③

活层 insert 出来的条目，dump 把来源写在脸上。bundle 层标包名，活层标那份 patch 文件的绝对路径，两种来源在同一次 dump 里并存，「这条是谁塞进来的」从不用猜。 test_entry_lands_in_composed_tree

/**
 * 最小插件：只用来证明「apply 执行了、带着什么 config」。
 *
 * 不 inject 任何服务、不注册路由、不碰 UI——刻意做到最小，这样「插件被
 * 加载了」这件事就没有任何别的解释。观测手段是写一个见证文件，而不是
 * 打日志：日志可能被吞、被缓冲、被格式变化骗过去；文件存在与否是硬事实。
 */
import { writeFileSync } from "node:fs";

/** 代码版本指纹。改了这个值就能证明跑的是新代码。 */
const MARKER = "lab-minimal-v1";

/** 模块顶层求值：模块被 import 的时刻。 */
const moduleLoadedAt = new Date().toISOString();

/**
 * @param {object} ctx    插件上下文（本项不用它）
 * @param {object} config 活层条目里 `config:` 那一坨，原样送到这里
 */
export function apply(ctx, config) {
  const witness = config?.witness;
  if (!witness) {
    throw new Error("lab-minimal: config.witness 是必需的");
  }

  writeFileSync(
    witness,
    JSON.stringify(
      {
        marker: MARKER,
        moduleLoadedAt,
        appliedAt: new Date().toISOString(),
        config,
      },
      null,
      2,
    ),
    "utf8",
  );
}
