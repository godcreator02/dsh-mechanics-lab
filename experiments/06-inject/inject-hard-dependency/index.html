06-inject / inject-hard-dependency

inject 是硬依赖，不是软等待

声明了 inject 的插件，它要的服务没到位就不执行 apply——这份契约有多硬：等不到，整条实例都起不来。

档次 ① 📗 复述型 ✅ 满覆盖 · 3 条用例 不需要 web

这一项讲的是什么

条目（entry，见 00-base/baseline-profile）在运行时对应一个 fiber——插件这一次生命的载体。一条插件除了被动等待挂载，代码里还能声明「我要用哪个服务」：模块顶层写 export const inject = [...]。条目上也能写这个字段，两处写法的关系已经在 01-entry/inject-field 钉死（条目级是补充，不会覆盖代码级），这一项统一用代码级写法。三个教学插件构成测试面：lab-registry 提供一个叫 labRegistry 的服务（service，插件之间互相提供能力的方式，见 01-entry/inject-field）； lab-alpha 声明依赖它；lab-open 是不声明依赖的对照插件。

这一项讲的是 inject 这条声明背后的契约本身：框架怎么保证，一条插件的 apply 真正被调用时，它声明要的服务已经全部就绪。谁先谁后由「服务几时就位」驱动、不看 patch 里的书写顺序，这条已经在 06-inject/activation-order 讲过，这里不重复；这一项要讲清楚的是这份「就绪保证」本身怎么运作——provider 怎么把服务摆上台面，框架靠什么把关，声明方的 apply 什么时候才被放行。

机制怎么工作

一条依赖声明从写下到兑现，走这四步——①②是声明与登记的两端，③是框架的把关动作，④是把关通过之后真正放行。

三个 profile，各自摆一种场景

三个 profile 起手都是空配方（make_minimal_profile），各自只 insert 本项要测的那几条。 谁 apply 了、谁没有，全靠见证文件裁决——插件在自己的 apply() 里落盘，文件在不在是硬事实，不用去猜日志。

读出来的是什么

①

inject 声明的服务不到位，apply 根本不执行。不是「apply 了但拿到 undefined」，是压根没 apply——官方文档已写明这条契约 （docs/official/zh/user/develop/framework/service.md:32）。provider 被禁用、服务连提供者条目都没有， 两条路径都验了这条。 test_provider_disabled_blocks_apply · test_service_with_no_provider_blocks_apply_and_kills_boot

②

等不到的下场很硬：那个条目永远停在 PENDING，boot 末尾的审计判它失败，整个实例起不来。 boot 审计本身的机制（为什么 PENDING 无条件致命）归 09-boot-vs-runtime/boot-audit，这里只用它的结论。 test_service_with_no_provider_blocks_apply_and_kills_boot

③

不声明 inject 就不受这条契约约束：它不排队，直接跑。lab-open 代码里不写 inject，运行时按需 ctx.get()，同一个从未存在过的服务对它没有任何阻塞——卡住依赖方的是声明本身，不是「服务不存在」 这个事实。 test_without_inject_declaration_runs_regardless

/**
 * 提供 `labRegistry` 服务：一本「谁登记过」的账本，谁登记一笔就立刻整份落盘。
 *
 * 落盘时机就是真实的 apply 先后关系——账本内容本身就是活的调用顺序凭证，
 * 不用另外拼事件流时间戳。
 */

import { writeFileSync } from "node:fs";

const MARKER = "lab-registry-v1";

export function apply(ctx, config) {
  const ledger = config?.ledger;
  if (!ledger) throw new Error("lab-registry: config.ledger（账本落盘路径）是必需的");

  const entries = [];
  const t0 = process.hrtime.bigint();

  const dump = () =>
    writeFileSync(
      ledger,
      JSON.stringify({ marker: MARKER, providedAt: new Date().toISOString(), entries }, null, 2),
      "utf8",
    );

  const book = {
    sign(who, note) {
      entries.push({
        who,
        note: note ?? null,
        ms: Number(process.hrtime.bigint() - t0) / 1e6,
        at: new Date().toISOString(),
      });
      dump();
    },
    list() {
      return entries.slice();
    },
  };

  // ctx.provide 返回的 disposer 在 fiber 卸载时自动调用，这里不用额外用 ctx.effect 包。
  ctx.provide("labRegistry", book);

  dump(); // 先落一次空账本，证明提供者自己先到位
}

/**
 * 依赖 `labRegistry` 的消费者。依赖声明写在代码里（`export const inject`）——
 * 这是主流写法，条目上也能写（见 01-entry/inject-field）。
 *
 * 拿不到服务时**不抛错**，如实记录 `gotRegistry`。探针在观测点抛错会把两种
 * 完全不同的现象混成一种：「inject 没满足 → 根本没 apply」 vs
 * 「apply 了但服务是 undefined」——前者见证文件不出现，后者出现且
 * `gotRegistry: false`，必须能分开。
 */

import { writeFileSync } from "node:fs";

const MARKER = "lab-alpha-v1";

export const inject = ["labRegistry"];

export function apply(ctx, config) {
  const book = ctx.get("labRegistry");

  if (book) {
    book.sign("lab-alpha", config?.note ?? null);
  }

  if (config?.witness) {
    writeFileSync(
      config.witness,
      JSON.stringify(
        {
          marker: MARKER,
          appliedAt: new Date().toISOString(),
          gotRegistry: book !== undefined && book !== null,
        },
        null,
        2,
      ),
      "utf8",
    );
  }
}

  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" }

/**
 * 对照插件：代码里**不声明** `inject`，运行时按需 `ctx.get()`。
 *
 * 用来验证「不声明依赖就不等」——apply 立刻跑，服务不在就是 undefined，不阻塞。
 */

import { writeFileSync } from "node:fs";

export function apply(ctx, config) {
  const registry = ctx.get("labRegistry");

  if (config?.witness) {
    writeFileSync(
      config.witness,
      JSON.stringify(
        {
          marker: "lab-open-v1",
          appliedAt: new Date().toISOString(),
          gotRegistry: registry !== undefined && registry !== null,
        },
        null,
        2,
      ),
      "utf8",
    );
  }
}
