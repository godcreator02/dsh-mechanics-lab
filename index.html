热与冷的边界

改一个文件，什么时候秒级生效、什么时候必须重启整个实例？这份文档把答案从「读源码推理」 钉成「跑实验实测」。核心结论只有一句：「要不要重启」问错了问题——真正要问的是， 你动的东西撞在哪一个快照面上，以及那个快照面有没有人负责刷新。

01

先拆一个术语陷阱：bundle 指两样东西

分不清「开发热加载」和「bundle 热加载」是有客观原因的：bundle 这个词在 DSH 里指两个完全不同的东西， 而它们恰好落在热/冷光谱的两个极端。把这两个先分开，后面所有判定才立得住。

02

一棵树是怎么叠出来的

DSH 底下是 Cordis 的 loader。你启动的不是「一个程序」，是一棵组合树。 profile 就是这棵树的配方——而配方的根永远是空数组： cordis.yml 里就写着 []，且每次启动都被无条件重写 （防止 loader 的 tree write-back 把已组合的行烤进文件，下次启动 bundle 的 insert 会翻倍）。

整棵树 100% 由 patch 叠出来。点下面任一层看它做了什么：

第 3 层是个隐藏耦合点

$DSH_HOME/cordis.patch.yml 这一层在很多项目文档里都没有记载，但它真实存在， 而且优先级压过每个 profile 自己的活层。源码注释称它是 "machine-local preferences that apply to every profile"。

现实影响：主实例和全部沙箱共享同一个 home 时，往这个文件写一笔会同时打进所有实例。 实测拿一份 home 层同时压中了两个互不相干的 profile，且 --patch overlay 的优先级比它还高。 已实测 · E2

03

patch 的三种语义，和一个会咬人的细节

一个 patch 项就是一个 YAML 对象，按它带不带 insert / id 分三种走法：

形态语义失败时
- insert: [...]
无 id		 条目追加到根列表末尾。新增插件的唯一姿势。 —
- insert: [...]
有 id		 追加进该 id 指向的 group 条目里。 目标不是 group → 警告并跳过
- id: X
加若干字段		 定位已存在条目，改它的字段。 找不到 id → 只警告，静默跳过

会咬人的细节：config 是整字段替换，不是深合并

源码里这段是全部的真相（cordis-plugin-include 的 applyEntryPatches）：

// 定位到目标条目后：
for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value        // ← 整字段替换，不是 merge
}

dsh-base 的 patch 文件开头也把这件事写成了设计约束： "A patch replaces the targeted row's whole config rather than merging into it"， 并由此推出「按模式取值不同的条目不能住在 base 里，每个 mode bundle 必须完整重述自己那份配置」。

注意「整字段」而不是「整条目」：patch 里没出现的字段不受影响。 只写 disabled: true 不会清空 config——实测三个键原样保留。 而只要写了 config，里面没重述的键就当场消失。 已实测 · E1

    这条细节对 dshw 的现实风险 · 已实测确认
    

      dshw 的 attach 账本往活层写 hmr 条目时，把 base / debounce /
      root 每次都写全了，所以目前安全。实验复刻了这个双条写法，并试了「只写 root」的变体：
      base 和 debounce: 1000 双双消失，
      debounce 静默回落 schema 默认的 100ms——挂着多条分发线的主实例会就此退回半截热载竞态。
    

    

      结论：账本块每条都写全不是冗余，是必须的。

    05
    
快照面：真正的判据

  


  

    「要不要重启」是问错了问题。正确的问法是：这个变更要生效，得让哪个缓存失效？
    而那个缓存有没有人负责刷新？ 有人刷的就热，没人刷的就必须重启。
