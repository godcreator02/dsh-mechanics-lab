# 教学线

## 假设清单

- 读者手边有一个能跑的 DSH，能建 profile、能起实例——照着做的时候可以真跑出结果
- 读者会写 Node，不需要解释什么是模块、什么是包
- 第一章走完的标志是「能独立写插件并自己排错」，不是「理解整套机制」
- 现有十课研究档案（`experiments/l0*`）里的判定与用例是可靠素材，各章从中取材

---

## §1 需求

### §1.1 做什么

给零基础读者一条**能走通的路径**：从跑起一个实例，到写出自己的插件，到交付给别人用，
最后到能自己查清楚「它为什么没跑」。

编排原则是**从使用角度由易到难**，不按概念分组：

- **每一项都是一个动作或一个具体问题**，不是一组概念。标题写读者想干的事
  （「把自己写的东西挂上去」「它挂了会连累谁」），不是知识点的名字（「条目的字段」）
- **同一个概念可以出现两次：先用后懂。** 第一次照着写就行、不解释；等读者用熟了、
  并且撞上了需要理解它才能解决的问题时，再回头展开
- **不从最底层起手。** 不先讲树的结构那类认知——那本身就有难度，而且读者此刻
  没有任何东西可以挂靠

三条硬约束：

- **一次只引入一个新词**，前面没出现过的术语不许突然使用
- **只给正确认知**——探索期的弯路、被推翻的判断、未坐实的观察一概不进
- **读者什么都不用做**：跑一条命令看输出。实验自己起隔离的实例、自己收数据

### §1.2 不做什么

- 不覆盖全部机制细节——`docs/SYLLABUS.md` 那套按机制层次排的十七课服务于
  「理解整套系统」这个另外的目标，两条线并存、各管各的
- 不做交互式练习、在线运行环境、视频
- 不把探索过程写进任何一页

### §1.3 需求边界

**算本主题的事**：分几章、每章几项、每项是什么动作、哪些概念先用后懂、
术语按什么顺序引入、每项的实验验什么、页面长什么样。

**不算的**：研究档案那条线的组织、`docs/SYLLABUS.md` 十七课的结构本身。

### §1.4 宏观验收

- 没写过 DSH 插件的人照着第一章走完，能独立写出带 `config` 的插件并跑起来
- 遇到「挂不上」和「挂上了没执行」两类问题时，知道分别该查什么
- 走完第二章，能把插件交付给别人用，并说得出四种交付方式各自的代价
- **术语零前引**：任意一项里出现的词，要么是通用编程词汇，要么在前面某项被引入过
- **每一项都能单独跑通**，读者停在任意一项手上都有能跑的东西
- 每一项的判定都有该项自己的用例支撑，用例跑绿
- 任何一页都不出现「我们当时以为 / 后来发现 / 这条被推翻了」

## §2 artifact 定义

**每一项是一个自足单元**：一组用例（验这一项的判定）＋ 一个教学页面（讲这一项的事）。
少数纯说明的项没有用例，页面上明确标出。

```
第零章 · 准备
├─ 0-1  环境与隔离            怎么跑、假 home 在哪、为什么碰不到你自己那个 DSH
├─ 0-2  探查器                它凭什么能看见整棵树 / 它看不见什么
└─ 0-3  最小实例              timer + hmr，一个实例的下限

第一章 · 会用
├─  1  把自己写的东西挂上去    apply / insert
├─  2  给它传配置              config
├─  3  临时关掉它              disabled / fiber
├─  4  挂不上，怎么查          排错① · 路径还是包名
├─  5  改了代码立刻生效        hmr / root
├─  6  配置不止一处            两处 patch，会拼起来
├─  7  改别人已经挂上的条目    insert 是加，裸 id 是改
└─  8  挂上了但没执行          排错② · inject 与 PENDING

第二章 · 交付：把它做成一个真的插件
├─  9  四种交付途径            单文件 / link / 正经安装 / worktree 双线
├─ 10  bundle 层与活层的分水岭  为什么正经安装必须重启；包怎么自注册
├─ 11  worktree 双线换版本      换 tag 就换版本，进程不重启
└─ 12  client 半边              一个包活在两侧

第三章 · 出错：它挂了会连累谁
├─ 13  apply 抛错              启动期 vs 运行期，两种下场
├─ 14  事务回滚的真实形态      运行期回滚，旧的一个不少吗
└─ 15  PENDING 连锁            A 挂不上，inject 了 A 的 B 会不会沉默

第四章 · 生死：卸载时到底清了什么
├─ 16  卸载连锁                拆一个，孩子和依赖它的怎么办
└─ 17  effect 与 disposer      路由？定时器？监听器？漏了哪个

第五章 · 热：活着的树怎么变
├─ 18  热重放 vs 热重载        改 patch 和改代码，事件流里怎么分辨
├─ 19  改一处波及几个          条目级 diff 到底 diff 在哪一层
└─ 20  hmr 自己被重载时        收口 · 它就住在自己的射程内
```

第零章用 `0-x` 编号、不占正式序号——准备工作跟正课分得开，第一章这才从 1 开始。

### 先用后懂：概念的两次出现

这是本编排的特征，也是它跟「一章讲一组概念」的根本区别：

| 概念 | 第一次（照着用） | 第二次（展开原理） |
|---|---|---|
| `timer` / `hmr` | 0-3：一个实例的下限就这两条 | 第 5 项：hmr 盯着文件，给它 root 就热重载 |
| `inject` | 第 1 项：照着写，它保证观察器先就位 | 第 8 项：等不到就卡住，整个实例陪葬 |
| `insert` | 第 1 项：加一条，指向你的插件 | 第 7 项：insert 是加、裸 id 是改 |
| patch 文件 | 第 1 项：就是这个文件，加行就行 | 第 6 项：它有好几处，各处写的会拼起来 |
| 挂不上 | 第 4 项：多半是 `name` 找不到东西 | 第 13–15 项：一条挂不上会连累整棵树 |

### 第二章：四种交付途径

第一章教出来的插件是「profile 目录里的一个文件」——那不是能给别人的东西。
第二章回答「怎么交付」，四条路横向对比：

| 途径 | 怎么交付 | 换版本时 |
|---|---|---|
| 单文件 | 扔进 profile 目录，`name` 写相对路径 | 改文件，hmr 重载 |
| link 成包 | 目录链接 ＋ 依赖声明，`name` 写包名 | 同上 |
| 正经安装 | 官方安装命令装进 profile，走 **bundle 层** | **必须重启** |
| worktree 双线 | 依赖指向一个钉在 tag 上的工作副本 | **换 tag 即换版本，进程不重启** |

这一章最值钱的两条对照：

- **bundle 层 vs 活层**：同样是「写 patch 的地方」，活层秒级热重放、bundle 层是启动
  闭包快照，改了必须重启。第 6 项只讲了活层那两处，这里补上第三处
- **正经安装 vs worktree 双线**：同样是「换一个版本」，一个必须重启、一个热生效

⚠️ **worktree 双线要写成通用模式**（git worktree ＋ 依赖指向钉 tag 的副本），
不绑定任何特定工具链。

## §3 技术

**用例**：沿用现有实验台（假 home 物理隔离、端口按 worker 分段、各项并行跑）。
每项的用例只验这一项的判定，不提前用到后面才引入的概念。

**观测**：采集器 `observatory/lab-recorder` 作为底层依赖——它 `provide` 一个上报口，
教学插件 `inject` 它、通过它说话。于是「插件说的」和「框架说的」进同一条事件流、
共用一套时间轴，先后关系直接读得出来。读事件流用 `experiments/lab/events.py`。

⚠️ 第三到五章的判定超出现有观测能力：看「effect 清了什么」需要直接读 fiber 的
effect 列表，看「哪些条目被重挂」需要条目级 diff，运行期实验需要「改文件 → 等 →
再看」的时序控制。那三章开工前先扩观测手段。

**页面**：自包含单文件，样式与脚本内联，无外部资源，双主题。动画用原生 CSS 与 JS，
不引图表库；每页的动画演示**这一项的那件事**，不复述整体结构。

**页面上的数据一律取自实验跑出来的产物**——时间线、报错原文、文件树、配置内容，
不手抄、不转述。

**命名**：页面按主题命名而不是按序号（序号只出现在页面内容与索引页里），
这样插入新项不必重命名文件。

**入口**：索引页列出完整六章树与各章状态，是读者看全貌的地方。

**与研究档案的互指**：每页底部标注本页判定由哪些实验验证。
