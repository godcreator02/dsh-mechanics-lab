# 教学线

## 假设清单

- 读者手边有一个能跑的 DSH，能建 profile、能起实例——照着做的时候可以真跑出结果
- 读者会写 Node，不需要解释什么是模块、什么是包
- 主干走完的标志是「能独立写插件并自己排错」，不是「理解整套机制」
- 现有十课实验里的判定与用例是可靠素材，九步从中取材

---

## §1 需求

### §1.1 做什么

给零基础读者一条**能走通的路径**：从跑起一个实例，到写出自己的插件，到遇到问题时知道该查什么。

编排原则是**从使用角度由易到难**，而不是按概念分组：

- **每一步都是一个动作**，不是一组概念。步骤的名字是读者想干的事（「挂上去」「关掉它」「挂不上怎么查」），不是知识点的名字（「条目的字段」「patch 的三种语义」）
- **同一个概念可以出现两次：先用后懂。** 第一次照着写就行、不解释；等读者已经用熟了、并且撞上了需要理解它才能解决的问题时，再回头展开原理
- **不从最底层起手。** 不先讲「插件被组织成一棵树」这类结构性认知——那本身就有难度，而且读者此刻没有任何东西可以挂靠

三条硬约束：

- **一次只引入一个新词**，前面没出现过的术语不许突然使用
- **只给正确认知**——探索期的弯路、被推翻的判断、未坐实的观察，一概不进教学线
- **每一步都能自己验证**：照着做能亲眼看到结果，不是只能点头

### §1.2 不做什么

- 不覆盖全部机制细节——主干只走能让人上手的那条线，深水区另开一区供选读
- 不做交互式练习、在线运行环境、视频
- 不把探索过程写进任何一步：弯路、推翻、未坐实的观察全部留在探索历史档案里

### §1.3 需求边界

**算本主题的事**：主干有几步、每步是什么动作、哪些概念先用后懂、术语按什么顺序引入、每步的实验验什么、页面长什么样。

**不算的**：SYLLABUS 十七课那套按机制层次排的结构本身（它继续存在，服务于「理解整套机制」这个另外的目标）、探索历史档案的写法。

### §1.4 宏观验收

- 一个没写过 DSH 插件的人照着主干走完，能独立写出一个带 `config` 的插件并让它在实例里跑起来
- 遇到「挂不上」和「挂上了但没执行」这两类问题时，知道分别该查什么
- **术语零前引**：任意一步里出现的词，要么是通用编程词汇，要么在前面某一步被引入过——这条可机械检查
- **每一步都能单独跑通**：读者停在任意一步，手上都有一个能跑的东西，不是半成品
- 每一步的判定都有该步自己的用例支撑，用例跑绿
- 主干任意一步都不出现「我们当时以为 / 后来发现 / 这条被推翻了」这类叙述

## §2 artifact 定义

**九步，每步是一个自足的单元**：一组用例（验这一步的判定）＋ 一个教学页面（讲这一步的动作）。

每一步的标题都是一个动作：

| 步 | 读者要干的事 | 这一步只说这些 |
|---|---|---|
| 1 | **让一个空实例跑起来** | 最小集合就是 `timer` 和 `hmr` 两条，照着写。它们是什么、为什么要它们——**不展开** |
| 2 | **把自己写的东西挂上去** | 一个导出 `apply` 的模块；patch 里加一条 `insert`；怎么确认它真的跑了 |
| 3 | **给它传配置** | 条目上写 `config`，`apply` 里收到 |
| 4 | **临时关掉它** | `disabled: true`，不用删条目 |
| 5 | **挂不上，怎么查** | `name` 写法与它对应的找法；最常撞的几种写错 |
| 6 | **改了代码想立刻生效** | 给第 1 步那个 `hmr` 配上 watch root——**此时才回头说明它是干嘛的** |
| 7 | **配置不止一处** | profile 的 patch 与 home 的 patch，后面的压前面的 |
| 8 | **改别人已经挂上的条目** | 前七步一直在 `insert`（加一条）；裸写 id 是**改**已有的那条——**此时才展开两种语义的差别** |
| 9 | **挂上了但没执行** | 服务与 `inject`；等不到就停在那儿，而且会让实例起不来 |

走完第 9 步，读者能写插件、能排错、能热开发。**主干到此为止。**

**深水区**（选读，不在主干里，读者遇到具体问题时才来）：树的真实结构（整体全景、`--dump-config` 看不见的那个条目、层级归属）、条目的生命周期（加载顺序、boot 审计、卸载连锁、effect 与 disposer）、hmr 自身的归属。

### 先用后懂：概念的两次出现

这是本编排的特征，也是它跟「一章讲一组概念」的根本区别：

| 概念 | 第一次（照着用） | 第二次（展开原理） |
|---|---|---|
| `timer` / `hmr` | 第 1 步：最小集合就这两条 | 第 6 步：hmr 是监听文件变化的那个，给它 root 就能热重载 |
| `insert` | 第 2 步：加一条，指向你的插件 | 第 8 步：`insert` 是加、裸 id 是改，两种语义 |
| patch 文件 | 第 2 步：就是这个文件，加行就行 | 第 7 步：它有好几处，后面的压前面的 |
| 条目没生效 | 第 5 步：多半是 `name` 找不到东西 | 第 9 步：也可能找到了、但在等一个服务 |

**第 1 步不解释「树」。** 那个结构性认知本身就有难度，而且读者此刻手上没有任何东西可以挂靠——它属于深水区，等读者已经挂过好几个插件、想知道「它们之间是什么关系」时才有意义。

### 每一步的固定结构

要干什么 → 照着做（最小操作） → 你会看到什么 → 出错了往哪看。

读者可以只看「照着做」那段就往下走，理解留给愿意停下来的人。

### 页面组织

**一步一页，加一个入口页**，入口页列出主干九步和深水区。每页自包含，可以被直接落地阅读而不依赖前面的上下文（前面步骤引入过的词，在本页给一句话回顾）。

## §3 技术

**用例**：沿用现有实验台（`make_minimal_profile()` 基线、假 home 物理隔离、端口按 worker 分段、各步并行跑）。每步的用例只验这一步的判定，不提前用到后面步骤才引入的概念。

**页面形态**：自包含单文件，样式与脚本内联，不引任何外部资源。双主题，跟随读者系统设置。

**演示手段**：动画用原生 CSS 与 JS 实现，不引图表库。每一步的动画演示**这一步的那个动作**，不复述整体结构——第 7 步演示「后面一层怎么压掉前面一层」，第 9 步演示「一个条目卡在那儿等一个不来的服务」，各演各的。

**术语引入表**：维护一份「词 → 首次引入于第几步 → 展开于第几步」的对照。它同时服务两件事——机械检查零前引，以及标记哪些概念是「先用后懂」的、第二次在哪。

**与研究档案的互指**：每页底部标注本页判定由哪些实验验证，链接到对应的研究档案。想深挖的人有路可走，不想的人不受打扰。
