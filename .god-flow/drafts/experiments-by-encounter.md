# 实验按遭遇顺序重组

## 假设清单

- 本项目唯一的产物是实验台。判定的家是**各实验自己的 README**，页面不是结论载体
- 现有实验里跑绿的判定是可靠素材，重组只改归属与命名，不重新验证已成立的结论
- **排序的参照系是「用 DSH 的人多久撞上它一次」，不是任何具体下游工具的用法。**
  参照系必须是抽象的使用频率——盯着某个消费者排，选题会缩到它用到的那几个点，
  观测信号也会跟着从「这个用法安不安全」出发，而不是从「这个机制怎么工作」出发
- 观测方法论（CLAUDE.md 第五节）与信息源三档（第六节）不因重组改变
- 「一个实验目录 = 一个假 home = 一个归档标签」这条隔离机制不动
- 未覆盖的机制照样进大纲树、标成未覆盖——**这棵树是覆盖清单，不是完工清单**

## §1 需求

### §1.1 做什么

把 `experiments/` 重排成一棵**按遭遇频率分档**的覆盖树：DSH 插件系统有哪些机制、
每个机制归哪一组、由哪个实验项负责、验没验过、**该先做还是后做**。

两条正交的轴，各管各的：

- **组**回答「这个机制归谁管」——一个机制一个家，不因为排序被撕开
- **档**回答「什么时候做它」——**标在项上，不标在组上**

档标在项上是本方案的关键。标在组上就必然出现一个叫「边界情况」的杂物抽屉，
而边界本来该住在它所属的那个机制旁边。

三档：

| 档 | 含义 | 谁会撞上 |
|---|---|---|
| ① | 天天碰 | 写插件、装插件、改完要生效——每个用 DSH 的人 |
| ② | 要懂才用得好 | 想让结果可预测、想知道自己改的东西波及多远 |
| ③ | 深水区与边界 | 造服务的人；以及出了事回头查的人 |

### §1.2 不做什么

- 不做教学编排——先用后懂、术语引入顺序、最短路径，全部撤掉
- 不按任何下游工具的用法排——档次判据只有抽象的遭遇频率
- 不因为排序而缩减覆盖面：三档的项一项不少，只是排在后面
- 不重跑、不重验已经跑绿的判定
- 不动实验台的隔离机制（假 home、端口分段、会话锁、产物归档）
- 不动 `docs/official/` 快照与它钉的版本

### §1.3 需求边界

**算本主题的事**：分几组、每组管哪些机制、每项归哪一档、项的命名与粒度、
判定与证据住哪、覆盖状态怎么标、`site/` 与 `docs/SYLLABUS.md` 在新格局里是什么角色。

**不算的**：`observatory/` 的实现、`experiments/lab/` 包的接口形态、
`docs/trajectory/` 的组织、各实验项内部的用例怎么写。

### §1.4 宏观验收

- 树上任一机制点，能一眼答出**哪一项管它、验没验过、该什么时候做**
- 同一个机制不由两项分别负责——拿一个有特征的短语 grep，只命中一处
- **没有一个组叫「边界」「其他」「杂项」**——每条边界都住在它所属的机制旁边
- 每项的判定住它自己的 README，别处只提名不复述
- 全套仍能并行跑：端口段不超十个，用端口的项互不撞
- 目录名一眼看得出这一项验什么，不需要打开文件才知道

## §2 artifact 定义

一棵**两级树**：功能组 / 实验项。

- **组**是机制的归属面。编号提供稳定排序，顺序大致跟着档次走，但**组不代表档**
- **项**是一个能单独跑的实验，**一项一个目录**：一份用例、一份 README、一份本项专用的
  教学插件。README 里是这一项的判定与证据，原始观测归 `out/results/`
- **每项两个标注**：覆盖状态（**✅ 已验** / **⚠️ 部分** / **⬜ 未覆盖**）与档次（①②③）

**档次不进目录名。** 档会随认知变化，而目录名同时是假 home 与归档标签——跟着档改名，
等于每次调整优先级都要动隔离机制。档只活在覆盖清单里。

## 大纲树

### 00 harness · 实验台自身与最小基线

不测 DSH，测的是**这台仪器能信到什么程度**、以及后面每一项站在什么地基上。

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `recorder-reach` | ① | 采集器听得见别的条目、自己也是棵树上的普通条目没有特权、挂载之前的历史是**丢的**不是没发生 | ✅ |
| `minimal-profile` | ① | profile 最少需要哪几个文件、`cordis.yml` 谁建、配方能不能是空的、空树谁保持进程活着 | ✅ |
| `framework-fallback` | ① | 兜底补 timer / hmr：判的是**服务**不是条目，而且关不掉 | ✅ |
| `baseline-profile` | ① | 基线 profile 的形状与它保证了什么：树形完全可预测、事件流降到十几条 | ✅ |
| `isolation-guarantees` | ② | 假 home 按项分、端口按 worker 静态分段、会话锁、产物归档——这几条隔离靠的是机制不是纪律 | ⬜ |

### 01 entry · 条目

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `field-vocabulary` | ① | 只有六个字段；id 是树内地址、name 是模块解析名，两者互不相干 | ✅ |
| `config-delivery` | ① | `config` 原样送达 apply、任意 JSON 形状都不变形、没写与写错键名结果一样 | ✅ |
| `disabled` | ① | 不挂载不是删除；`!!js` 表达式的求值时机 | ✅ |
| `name-resolution` | ① | 三条解析路径；`internal` 分支是否激活；Windows 裸盘符 vs `file://` URL；`exports` 子路径要显式声明；相对路径没有回退链；`cordis:` 未知内置项与裸包名找不到是**两种不同的报错机制** | ✅ |
| `inject-field` | ② | 条目上的 `inject` 与代码里声明的是**补充不是覆盖**，绕不开代码里那份 | ✅ |

### 02 recipe · 配方怎么叠出来

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `layer-stack` | ① | 四层叠加顺序与来源注释；同 id 跨层的优先级与每层的中间态；home 层缺失等价无层、内容非法要 fail loud；overlay 按 argv 顺序且压过 home 层 | ✅ |
| `insert-semantics` | ① | `- insert:` 不带 id 追加进根组、带 id 是**指目标 group**、目标不是 group 时警告跳过 | ✅ |
| `override-semantics` | ① | 裸 `- id:` 覆盖：`config` 是整体替换不是深合并、没写的字段不受影响、`null` 的语义、野字段原样带着没人读、找不到 id 只警告跳过且不影响同批其余 | ✅ |
| `cross-layer-targeting` | ② | 后面的 patch 能改前面 insert 进来的条目 | ✅ |
| `dump-fidelity` | ② | 静态算出来的配方与运行时挂载走的是同一段 compose，不是近似——这是「静态验证算数」的全部依据 | ✅ |

### 03 supply · 插件从哪来

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `four-ways` | ① | 同一个插件四种挂法，挂出来的条目没有任何区别 | ✅ |
| `self-registration` | ① | 包自注册要两样齐备：包里声明 patch、包名进 bundles 名单；缺一样什么都不发生 | ✅ |
| `pinned-worktree` | ① | 依赖指向一个钉在 tag 上的工作副本，换 tag 即换版本；开发副本与钉住的副本互不干扰 | ✅ |
| `supply-x-activation` | ② | 供给 / 激活 / 版本钉法三条正交轴的横向对照 | ✅ |
| `install-command` | ② | 官方安装命令到底改写了 profile 的什么（**按安装后的实际状态对账**，不实跑、只走源码） | ⚠️ |
| `client-side` | ③ | 带浏览器端的包怎么被认出来：按包名增量扫描 + **永久负判缓存**，负判进了缓存补声明也没用 | ⬜ |

### 04 replay · 配方热重放

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `replay-mechanism` | ① | 活层文件一改，换掉的是那个幽灵条目的 config，重新 compose 的只是它的子树 | ✅ |
| `cold-surfaces` | ① | 哪些面是冷的：bundle 层 patch 文件、bundles 名单、overlay 文件——同一个根因，没有代码在监听它们 | ✅ |
| `replay-granularity` | ② | 条目级 diff：只有变化的条目重挂；但所有条目的 options 都被无差别替换一遍，只是 fiber 没动。**观测信号必须落在被改动的那个条目上** | ⬜ |

### 05 reload · 代码热重载

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `watch-root` | ① | 监听范围的语义：默认值、绝对路径、指着别处、空数组 | ✅ |
| `ignore-rules` | ① | 忽略规则怎么让 junction 那一头的代码够不着；把点开头那条规则拿掉就立刻热了 | ✅ |
| `reload-unit` | ① | 重载的单位是**插件入口**不是被改的那个文件——改一个被 import 的辅助文件，整个入口重来 | ✅ |
| `new-code-old-config` | ① | 同一时刻改代码又改配方，拿到的是新代码配旧配方 | ✅ |
| `reload-debounce` | ② | 一次 checkout 换掉四个文件，只重新加载一次 | ✅ |
| `cold-reads` | ② | apply 期直接读的文件从没进过模块缓存，所以是冷的 | ✅ |
| `reload-while-busy` | ② | 正干着长活儿时被重载：那件活儿的下场、旁观者手上的服务对象、会不会把整棵树拖住 | ✅ |
| `client-swap` | ③ | 浏览器端产物内容变了之后的热换链路：轮询 → 重算摘要 → 换版本号 → 推给浏览器 | ⬜ |
| `hmr-self` | ③ | hmr 自己就住在自己触发的那次重放的射程里：改它的 config 会不会把 patch 监听自断且不恢复；更新钩子能不能否决重启 | ⬜ |

### 06 inject · 用别人的服务

写插件天天写的那一半。**造**服务归 08。

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `inject-hard-dependency` | ① | `inject` 是硬依赖：服务没到位 apply 根本不执行，部分满足也照样拦，依赖全有全无 | ✅ |
| `activation-order` | ① | 书写顺序不决定加载顺序——所有条目并发创建，谁先 apply 由服务就位顺序决定 | ✅ |
| `dependency-chain` | ② | 二级依赖怎么传递；缺提供方与缺中段各断在哪一环 | ✅ |
| `teardown-chain` | ② | 被依赖者下线时依赖方自动卸载，服务恢复后自动重载 | ⬜ |

### 07 tree · 运行时的树

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `recipe-vs-tree` | ② | 配方 ≠ 树：多一个幽灵条目，且整份配方就装在它的 config 里，所以它必然自指、必然看不见 | ✅ |
| `hierarchy` | ② | 归属由 config 的嵌套结构决定，不由 patch 文件里的书写位置决定；group 怎么造出嵌套子树 | ✅ |
| `disabled-propagation` | ② | 禁用向下传播，以及 group 自己照常激活、孩子拿不到 fiber 这个例外 | ✅ |
| `entries-order` | ② | 扁平遍历的顺序不稳定——不反映创建时间也不反映树位置，只有 `parent` 能信 | ✅ |

### 08 service-core · 自己造服务与副作用

cordis 的运行时内核。写插件的人用它的产物，造框架件的人才动它。

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `provide` | ③ | 提供服务的两种写法（裸对象挂名字 / 继承服务基类）、以及「此刻手上这份 ctx 属于谁」 | ✅ |
| `one-owner` | ③ | 一个名字一个主人，第二个来占的当场失败——两种写法混着占也一样 | ✅ |
| `registry` | ③ | 多实现并存的办法是绕开独占、不是打破它；表空时会怎样 | ✅ |
| `availability-contract` | ③ | 使用方能不能跑，由提供方自己声明的可用性说了算，不由「怎么安排多个实现」决定 | ✅ |
| `isolate` | ③ | 隔离组各自持有同名服务的不同实例（**负面对照未测**） | ⚠️ |
| `leak-on-reload` | ③ | 清理写漏的那版，重载之后旧的副作用照样触发，两份并存 | ✅ |
| `module-state-reset` | ③ | 重载把模块顶层的状态归零 | ✅ |
| `effect-vs-raw` | ③ | 注册副作用时包不包 `ctx.effect`，卸载之后的差别 | ⬜ |

| `effect-inventory` | ③ | 直接读 fiber 上的 effect 清单——把「它还在不在」从间接推断变成直接观测 | ⬜ |

### 09 boot-vs-runtime · 同一件事，两个时机两种下场

这一组不是「失败的杂物抽屉」，它有自己的机制内核：**同一种反常，启动期与运行期的
处置完全不同**。「致不致命」这个问题必须先问「什么时候」。

| 项 | 档 | 验什么 | 状态 |
|---|---|---|---|
| `boot-audit` | ③ | boot 末尾的普查：非 ACTIVE 一律抛错、退出码、判词长什么样，且**只做这一次** | ✅ |
| `boot-failure-shapes` | ③ | 启动失败的形态学——解析不到 / 依赖等不到 / 撞车，三种各自的出处与报错，**一条挂不上是整树陪葬不是跳过** | ✅ |
| `duplicate-id-timing` | ③ | 同 id 撞车：boot 期查重在创建任何条目之前，整个进程死掉；运行期撞同一个 id 被兜住 | ✅ |
| `pending-timing` | ③ | 等不到的依赖：boot 期无条件致命；boot 之后靠热重放新加的条目卡在 PENDING 安静待着 | ⬜ |
| `loader-self-deadlock` | ③ | 依赖 loader 服务会把插件锁死在 PENDING，而且日志里一个字都没有 | ⬜ |
| `externals-exit` | ③ | 入口依赖树里的文件一变，整个进程退出——唯一一条主动重启的路 | ⬜ |

## §3 技术

### 判定与证据住哪

| 东西 | 家 |
|---|---|
| 一项的判定与它的证据出处 | 那一项自己的 README |
| 原始观测（事件流、见证文件、账本、用例输出） | `out/results/` 的归档，不进 git |
| 全局覆盖清单（这棵树 + 状态 + 档次） | `docs/SYLLABUS.md` |
| 术语 | `docs/GLOSSARY.md` |
| 探索史 | `docs/trajectory/` |

`docs/SYLLABUS.md` 的内容换成这棵树：十组、每项的状态与档次、性质标记、依赖与开销。
教学装置（难度分档、最短路径、先用后懂、术语引入顺序）删干净——文件名沿用，
是因为项目里对它的引用都指着「全局覆盖清单」这个角色，角色没变。

`site/` 那批页面与项目根那份旧教材**全部删掉**。教材不再是产物，页面也不再是结论载体。
删之前先把只写在页面里的判定并进对应项的 README——那批实验目录没有 README，
判定此刻只活在 HTML 里，直接删就是丢结论。

### 一档往前排的代价

**三档的 `boot-audit` 与 `boot-failure-shapes` 排在最后，但一档的实验先用得上它。**
任何一项判「这次跑挂了」，都要认得出启动失败长什么样——退出码、判词、
以及「一条挂不上整树陪葬」这个前提。

所以一档实验里对启动失败的判断按**已知结论**用，不在那些项里重新论证；
到 09 组开工时再把这些结论坐实并回填。这是排序换来的代价，不是漏洞，
但它意味着 09 组一旦推翻某条前提，前面引用过它的项要跟着复核。

### 性质标记保留

📗 复述型 / 🔬 发现型 / ⚠️ 矫正型 三个标记**继续用**。它不是教学装置——它决定用例的
**断言强度**：对照式直接断言文档承诺的行为，观察式先如实记录再下判定，失败时的含义
完全不同。「开工第一件事是 grep `docs/official/`」这条纪律靠它落地。

### 命名

- 组名与项名一律英文小写、连字符分词
- 组带两位数字前缀，只为稳定排序
- 项名说清**验的是什么机制**，不用序号、不用「第几步」这类相对位置词
- 叶子目录名全局唯一——假 home 与归档标签都取自它，重名会让两项共用一个 home，
  而这种撞车只在并行下发作

### 并行

端口段十个是硬边界，扩不了。一项一目录之后项数远超 worker 数，靠给**用端口的项**
打并行分组标记把它们钉在固定 worker 上；不用端口的项随便分。
不做「取模复用端口」那种事。
