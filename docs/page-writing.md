# 实验说明页怎么写

`experiments/**/index.html` 的写作规范：装什么、怎么排、怎么措辞。
判定的唯一正本仍是各项 `test_*.py` 的模块 docstring，本篇只管页面。

## 一、读者是谁

**懂计算机，不懂 DSH。**

可以直接用、不必解释的：JavaScript 与 YAML 的读写，进程、标准输出、退出码，
Node 的模块解析与 `node_modules`，符号链接，依赖注入与生命周期这类通用概念，
以及「插件系统」这个词本身。

**必须解释的是 DSH 与 Cordis 专有的一切**：条目、fiber 与它的状态、服务与
`inject`、patch 的层叠、profile 的三件套、bundle、活层、幽灵条目、boot 与运行期
的分界。读者没读过官方文档，也没读过本仓的术语表。

判据很直接：一个词在别的插件系统里查不到同名同义的东西，它就得在页面上解释。

## 二、装什么：四层，缺一层页面就不成立

按这个顺序排。前两层讲原理、正面立机制，后两层给观测与判定；边界与盲区属于后两层，
不许提到前面去当开场白。

### 第一层：这一项讲的是哪个机制

开篇正面说清**这一项要讲清楚的是什么机制、它在整套系统里干什么活**。

⚠️ **开篇不抛盲区、不抛坑、不抛「有个反直觉的地方」。** 那些是读懂机制之后才接得住
的结论，提前抛出来读者只能囫囵咽下——他还不知道正常情况长什么样，无从判断哪里不对劲。
边界、盲区、反直觉的发现一律往后放，放在机制讲完之后（见下一节的正向在前）。

不合格的开篇有两种。一种是只报菜名：「lab-recorder 是后面每一项实验的地基——先看清
它自己的观测边界」，读者不知道 lab-recorder 是什么、什么叫观测边界。另一种是上来就
讲缺陷：「仪器自己也是一条插件，所以它有盲区」，读者连仪器怎么工作都还不知道。

合格的开篇正面立起机制：「插件系统在运行时会把每条插件的生命周期变化广播出来。
这一项讲的是怎么把这些变化接住、攒成一份能事后翻查的记录——本仓所有实验的数据都
从这份记录来。干这活的是 lab-recorder，它自己就是一条普通插件。」

### 第二层：机制怎么工作

**关键机制必须点名**——用它在源码或官方文档里的真名，不要发明代称、不要用比喻替代。
说「它 provide 了一个叫 `labObserver` 的服务，别的条目靠 `inject: ["labObserver"]`
声明依赖，框架保证被依赖的先就位」，不要说「它像一个广播站」。

比喻可以垫在真名后面帮理解，不能顶替真名出现。读者合上页面之后要能拿这些名字去
grep 源码、去搜官方文档；比喻 grep 不到。

这一层用分步舞台讲，一步一个环节，走完读者手里就有完整链条。链条讲不清就说明
这一项自己还没想清楚，先回去想。

### 第三层：实验看到了什么

现有的图、时间线、并置对照、数字。数字必须来自 `results/` 归档，footer 标明取自
哪一次。这一层是观测，不是判定。

### 第四层：读出来的是什么

结论卡片，每条标出它对应哪个 `test_xxx`。**判定的完整表述与证据链在 docstring**，
页面这里只给一句话结论加一个指路，不复述 docstring。

## 三、编排

两条硬规矩：正向在前，依赖向前。

### 正向在前，边界在后

**先把机制正常怎么运转讲完，再讲它的边界、盲区与反直觉之处。**

理由是读者要先有参照系才认得出异常。「它有盲区」这句话，对不知道它正常能看见什么
的人来说是空的；「拆干净再建是错觉」这句话，对不知道重载分几步的人来说也是空的。
反过来，正常流程讲透之后，边界往往一句话就够，因为读者自己已经能推到那一步了。

落到页面上：第二层机制讲完之前不出现「但是」「其实」「反直觉的是」这类转折。
本项的核心发现如果正好是一处边界（很多项都是这样），那它属于第四层的判定，
不是开篇的钩子。

### 依赖只能向前

**任何一处只能依赖它前面已经讲过的东西。**

具体到三个尺度：

- **页内**：术语第一次出现时就地定义，之后才能裸用。第 3 节不能用第 5 节才解释的词
- **组内跨页**：同组靠前的项已经讲过的可以直接用，但要提名让读者知道去哪补
  （「条目是什么见 `00-base/minimal-profile`」），不能默认读者读过
- **跨组**：`00-base` 讲过的，`01-entry` 之后可以直接用。反过来不行

检查办法是从头顺读一遍，遇到任何一个「还没定义就在用」的词就停下来补。这一遍必须
真读，不能凭印象——写的人天然认为自己讲过了。

三处例外不算违反：

- 通识词（第一节列的那些）
- 本页正在讲的那个机制自己的名字出现在标题里
- 已经在同一页更靠前的位置定义过、这里只是再次使用

## 四、术语怎么定义

第一次出现的写法：**真名 + 一句话说它是什么 + 它在这一项里管什么**。

反例是「hmr 会重新加载条目」——读者不知道 hmr 是什么、条目是什么。

正例是「条目（entry）是配方里的一行，描述『挂哪个插件、给它什么配置』；一条条目
在运行时对应一个 fiber，也就是这个插件这一次生命的载体」。

定义放在它第一次出现的地方，不集中堆在页首——集中堆就成了要背的词汇表，读者背不动。
术语的完整定义正本在术语表（`docs/GLOSSARY.md`），页面写的是一句话版；两者冲突时
以术语表为准，页面跟着改。

同一个词在 DSH 里指两样东西的（bundle、hmr、snapshot 都是），页面上第一次用就得
说清这里指哪个，否则读者会拿另一个意思往下读。

## 五、用语

- 中文，中文标点。技术专名、包名、字段名、命令保持原文
- 不写「显然」「众所周知」「不难看出」。读者不懂 DSH，对他没有什么是显然的
- 不写「详见源码」就完事——要么把结论说出来，要么指明是哪个文件的哪个函数
- 状态、字段、事件名一律用它们在事件流与 `--dump-config` 里的原样写法，
  不要翻译成中文再用（`ACTIVE` 不写成「已激活」，读者要拿它去对事件流）
- 页面出现的每个数字都标得出处，一个都不许编。文件树里的每个文件名同理，
  对着 `results/*/profiles/` 与本项 `fixtures/` 写

## 六、格式

页面是手写的、进 git。自包含单文件，样式与脚本内联，无外部资源，双主题
（`prefers-color-scheme` 与 `[data-theme]` 两套都要），原生 CSS 与 JS，不引图表库。

版心两栏：正文一栏（约 820px）、侧边文件树一栏（约 320px），整体居中。
窄屏并成一栏，树收到正文上方。

固定骨架，从上到下：

- `crumb`（组名与项名）、`h1`、`sub`（一句话点题）
- `tags`：档次、性质（复述型 / 发现型 / 矫正型）、用例数与覆盖程度、要不要 web
- 各小节
- `footer` 三行：判定正本在哪个 docstring、数字取自哪次归档、回到全部实验的链接

侧边栏与正文平行，常驻不随小节变化。

交互按内容性质选：

| 内容性质 | 用什么 |
|----------|--------|
| 过程（有时间顺序） | 分步，每步一句说明 |
| 查询（并置状态） | hover 为主加分步辅助 |
| 关系（结构性） | 静态加联动高亮 |

hover 是临时预览：它不改分步指针，指针计数器读的是当前钉住那一步，鼠标移开回落。
**不许自动播放**，节奏归读者。

### 侧边文件树

**整页一棵树，常驻侧边栏，可点开看文件真实内容。**

一棵树，不是两棵——假 home 那边和插件源码那边合成一棵，两个顶层分支：

```
实验现场
├─ $DSH_HOME/            假 home，这一项独占
│  └─ profiles/<名>/
│     ├─ cordis.patch.yml
│     └─ node_modules/<插件> →   junction，指向下面那支
└─ 插件源码
   └─ fixtures/<插件>/
```

junction 那行要指得出它落到插件源码那一支的哪个位置——这是读者理解「插件怎么被
找到」的唯一线索。

四条规矩：

- **树只放文件名，一行一个，别挂说明。** 侧栏只有 320px 宽，每行再挂一句话就会
  折成三四行，树立刻变成文字墙——那就不是树了。说明挪进点开后的内容面板，一句话
- **树不跟章节绑定。** 一页只有这一棵，不随分步高亮、不随小节切换内容。它是读者
  随时可查的参照物，不是页面用来指指点点的道具
- **点文件看内容。** 点一个文件行，展开它的真实内容；目录行不可点。同时最多展开
  一个，点另一个就换过去
- **完整不裁剪**，该有的层级一个不省

紧凑是硬指标：`font-size:11.5px`、`line-height:1.5`、行内 `padding` 不超过 2px，
整棵树扫一眼要能看出层级形状。缩进用制表画线字符，`white-space:pre` 原样保留。

文件内容**内联在页面里**（页面无外部资源，取不了远端），逐字取自
`results/<那一次>/profiles/` 与本项 `fixtures/`，**一个字符都不许改写或精简**。
内容长的放进带最大高度的滚动区。

⚠️ **内容不能经过「读出来再抄进去」这条路。** 工具展示文本时会把 CRLF 显示成 LF、
把 NUL 这类不可见字节直接吞掉——照着展示结果抄，抄出来的就跟磁盘对不上，而且看不出来。
必须字节级读写（`read_bytes` / `write_bytes`）直接拼进页面，落盘后再跟源文件比一遍。

侧边栏在正文旁边常驻（`position:sticky`），读者读到哪儿都能扭头看一眼树；窄屏
放不下就收到正文上方，别横向挤压正文。

读者要能随时把「页面在说哪个文件」和「这个文件里到底写了什么」对起来——
没有它，`insert` 块、`bundles: []`、`inject` 声明这些
词全靠读者脑补。

## 七、页面不装什么

- **不复述 docstring 的判定与证据链**。页面给一句话结论加一个 `test_xxx` 指路
- **不装时间戳、覆盖进度、待办**。归档目录名是数据不是标注，不受此限
- **不编数字、不编文件名**。归档里没有的就不上页面
- **不装未验证的观察**。0 用例的项整页标未覆盖、画缺口，视觉上必须跟已验项分得开

## 八、覆盖程度怎么标

页面要如实反映这一项验到什么程度，别让读者以为部分覆盖的项跟满覆盖的一样确凿。

- 满覆盖：`tags` 里绿色标用例数
- 部分覆盖：琥珀色标「部分覆盖」与用例数，正文里那些只有源码依据、没有用例断言的
  结论单独用弱化样式，跟有用例支撑的分开
- 未覆盖（0 用例、`results/` 是空的）：整页三层信号——琥珀色标签、顶部横幅明说
  这页画的是缺口不是证据、内容区套虚线框。主体画缺口：要验什么、为什么还没验、
  补上需要什么装置
