临时关掉它

不删那一条，只让它这次别跑。加一行 disabled: true 就行—— 但「关掉」和「压根没写」在树上是两件不同的事。

uv run pytest experiments/step4_disable_it/ -n 0 -s · 3 个用例 · 约 26 秒

现场

三次跑，patch 只差那一行

关掉它
- insert:
    - id: worker
      name: ./worker.mjs
      disabled: true
      config:
        班次: 早班
去掉那一行
- insert:
    - id: worker
      name: ./worker.mjs

      config:
        班次: 早班

插件文件三种情况下都照样放在 profile 目录里，其余配置一字不差。

跑出来

整棵树都动了，就它没动

PENDING LOADING ACTIVE 仪器 在树上，但从没动过

被关掉的那条仍然在树上——采集器睁眼时拍到了它，只是它从头到尾一个状态都没走过、一句话也没说。

采集器拍的那张起点快照里，它带着两个决定性的字段： 

disabled: true      hasFiber: false      状态: null

fiber 是这一步引入的新词：条目是你在 patch 里写的那一行，fiber 是它真跑起来之后的那个运行实例。 被关掉的条目连 fiber 都不建——所以它没有状态可走。

⚠️ 一个会认错的地方

光看「有没有 fiber」是不够的

上面那张快照里，timer 和 hmr 在那一刻也是「还没建 fiber」—— 它们只是还没轮到而已，后面就建起来跑完了。

所以在采集器睁眼那一瞬，「没有 fiber」并不区分「被关掉了」和「还没轮到」。 真正分得开的是接下来那十几毫秒：

hmr
LOADING → ACTIVE
include
ACTIVE
lab-recorder
ACTIVE
timer
LOADING → ACTIVE
worker
（一次都没变过）

判据是「别人都动了，就它没动」，不是「它没有 fiber」。 实验里也是这么断言的——先确认 timer 走到了 ACTIVE， 否则「worker 没动」也可能只是采集器根本没记上。

从「它没跑」这个现象看，两者一模一样；从树上看，一个在、一个不在。 这个区别在排错时很要紧：条目在树上说明 patch 被读到了、name 也没写错， 问题只在那一行开关上。

去掉那一行

它立刻就正常了

对比着看就清楚了：正常的条目是「fiber 先建好，再往下走」；被关掉的是连建都不建。 这就是「在树上但没有 fiber」的实际含义。
