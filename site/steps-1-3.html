插件加载的前 25 毫秒

三个实验，一台装在进程里的采集器。下面每条时间线都是真跑出来的——条目什么时候进 PENDING、什么时候开始 LOADING、插件自己在哪一刻说了话，全部读自同一份事件流。

先说仪器

它是树上的一条，不是外挂的探针

要看清插件加载时发生了什么，得有个东西在进程里听着。这台采集器叫 lab-recorder，它本身就是一个普通插件条目——写在同一个 patch 文件里， 跟被观测的东西平级，没有任何特权。所以后面每张图里你都会看到它。

它怎么听见框架说话

// fiber 每次状态变化触发一次，带旧状态。
// 这是抓住 LOADING 这种几毫秒窄窗口的唯一办法 —— 轮询必然错过。
ctx.on("internal/status", (fiber, oldValue) => {
  push("status", {
    id:   fiber.entry?.options?.id,
    from: FIBER_STATE[oldValue],
    to:   FIBER_STATE[fiber.state],
  });
});

FIBER_STATE 那张数字→名字的表得自己写死在代码里：它在 cordis 里是 TypeScript 的 const enum，编译后被内联成数字字面量，运行时根本不存在这个对象， import 不到。

它怎么让别的插件也能说话

// 框架事件只回答「框架对这个条目做了什么」，
// 回答不了「这个插件自己拿到了什么」—— 那只有插件自己知道。
ctx.provide("labObserver", {
  // 传一次自己的 ctx，采集器反查你在树上的 id ——
  // 比让插件自报名字可靠：它写死的名字未必等于条目 id
  for(callerCtx) {
    const who = whoOf(callerCtx);
    return (note, data) => push("report", { who, note, data });
  },
});

于是「插件说的」和「框架说的」进同一条流、共用一套时间轴—— 先后关系直接读得出来，不用去拼两份数据。

它的能力上限：拿不到自己挂载之前的历史。 采集器自己也要被加载，在它 apply 之前发生的事没人记——所以事件流第一批是 snapshot（睁眼时看到的样子），那之前的过程是丢的。 图上所有毫秒数都相对它睁眼那一刻，不是进程启动。

第 1 步

一个实例最少需要什么

只写 timer 和 hmr 两条。加上采集器，再算上框架自己放的树根， 一共四条——这是一个 DSH 实例能瘦到的极限。

现场

假 home 的全部内容
out/testhome/step1/
├─ profiles/
│  ├─ node_modules/   252 条，dsh 自建
│  └─ minimal/
│     ├─ package.json
│     ├─ cordis.patch.yml

│        └─ lab-recorder → link
├─ logs/

跑出来

PENDING 等依赖 LOADING 正在跑 apply ACTIVE 就绪 仪器
timer 变 ACTIVE
1.8 ms
hmr 才开始 LOADING

hmr 加载耗时
12.6 ms（1.9 → 14.5）—— 四条里最慢的

hmr 一直在 PENDING 等着，直到 timer 变成 ACTIVE 才开始加载。 顺序不是 patch 里的书写顺序决定的，是依赖决定的。

把 timer 那两行删掉再跑，实例根本起不来，退出码 1，日志点名： pending (waiting for service: timer)。这两条是捆绑的。

第 2 步

把自己写的东西挂上去

现场

profile 目录里多了一个文件
profiles/mine/
├─ package.json
├─ cordis.patch.yml
├─ hello.mjs          ← 就是它
├─ cordis.yml
└─ node_modules/
   └─ lab-recorder → link

插件就一个文件，扔进 profile 目录就行。没有 package.json、没有构建、 没有 npm install。仪器仍然走 link，因为它是个包。

hello.mjs — 一个插件的全部家当
export const inject = ["labObserver"];

export function apply(ctx, config) {
  // 先告诉观察器「是我在说话」
  const say = ctx.labObserver.for(ctx);

  say("我的 apply 被调用了");
}
cordis.patch.yml — 只在第 1 步的基础上多一块
# …前面 timer / hmr / lab-recorder 三条不变…

- insert:
    - id: hello
      name: ./hello.mjs   # 相对 profile 目录

跑出来

PENDING LOADING ACTIVE 仪器 / 插件说的话
采集器就绪
1.8 ms —— 它零依赖，所以最快
hello 开始 LOADING
1.9 ms —— 等到观察器了
hello 说话
2.4 ms
hello 变 ACTIVE
3.4 ms

说话在 2.4 ms，变 ACTIVE 在 3.4 ms —— apply 跑在「加载中」，不是「加载完之后」。 一个插件在自己的 apply 里是看不到自己 ACTIVE 的。

另一头也验了：文件原样放着、只是不写那一条，它就完全不存在——树上没有它，一句话也没说。 挂载只认 patch 里写没写，不会自己去扫目录。

第 3 步

给它传配置

插件只改一行：把 apply 的第二个参数报出来。四个变体各起一个实例， profile 目录结构跟第 2 步一样，只有 patch 里那段 config 不同。

echo.mjs — 跟第 2 步只差一行
export const inject = ["labObserver"];

export function apply(ctx, config) {
  const say = ctx.labObserver.for(ctx);
  // 单独报一次类型：undefined 进 JSON 会让整个键消失，
  // 不记类型就分不清「收到 undefined」和「压根没报这个字段」
  say("我收到的 config", { 类型: typeof config, 内容: config ?? null });
}

后两组结果完全一样，而且全程没有任何报错或警告。 patch 里多写一个没人认识的键，框架既不拦也不提醒——插件照常跑起来，只是拿不到配置。 所以接 config 要当成「可能没有」来写。
