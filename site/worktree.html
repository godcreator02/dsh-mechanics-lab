换个 tag 就换个版本

把包 link 进 profile 之后，「换版本」等于去那个目录里改文件——可那个目录同时也是你写代码的地方。 这一项把两件事分开：写代码在一个工作副本里，实例看的是另一个钉在 tag 上的副本。 发一次版就是在后者里 git checkout 一下，进程不重启。

uv run pytest experiments/ch2_worktree/ -n 0 -s · 5 个用例 · 约 54 秒

怎么搭

同一个仓，开出第二个工作副本

git worktree 能给同一个仓开出第二份文件。第一份跟着 HEAD 走， 平时改代码就在那儿；第二份用 --detach 钉死在一个 tag 上，谁都别想推着它动。 profile 的依赖指向第二份——从 profile 的角度看，那就是个普通的包， 跟上一项的 link 没有任何区别。

这次跑出来的两个副本
跟着 HEAD 的副本   …/out/testhome/ch2_worktree/repo       →  HEAD 9605225（第二版）
钉在 tag 上的副本  …/out/testhome/ch2_worktree/pinned-a   →  v1.0.0

profile 的依赖     greeter  →  钉在 tag 上的那个副本
实例起来之后，插件说的话
{'版本': '1.0.0', '招呼语': '早上好', '入口': '第一版'}

HEAD 那边已经在第二版了，实例说的还是第一版。 它认的是 tag，不是 HEAD——这正是「写到一半的东西不会被实例吃进去」的由来。

为什么要拆成三个文件

一句话里的三个字段，来自三个文件

这个包一共四个文件：入口一个，两个各只导出一个常量，再加 package.json。 插件跑起来只说一次话，一次把三个常量全说出来——万一某次只换了一半，这里立刻露馅。

version.js
export const version = "1.0.0";
greeting.js
export const greeting = "早上好";
index.js（入口）
say("我跑起来了", { 版本: version,
  招呼语: greeting, 入口: "第一版" });
↓ 两个 tag 之间，连 package.json 一共 4 个文件全变 ↓
version.js
export const version = "2.0.0";
greeting.js
export const greeting = "晚上好";
index.js（入口）
say("我跑起来了", { 版本: version,
  招呼语: greeting, 入口: "第二版" });

换版本跟第 5 项那种「改一行」不是一回事：一次落下的是一批文件。 要是这批被拆成好几次重新加载，中间就会出现「一部分新、一部分旧」的半截状态。

发版

就一条命令：git checkout v2.0.0

事件流（在钉住的那个副本里切 tag）
   1.6ms  report     greeter    我跑起来了  {"版本": "1.0.0", "招呼语": "早上好", "入口": "第一版"}
   …（实例正常跑着，中间用例自己等了一秒，让两拨事件分得开）…
1235.7ms  hmr-change            文件变了：package.json
1362.0ms  status     greeter    ACTIVE → UNLOADING
1362.2ms  status     greeter    PENDING → LOADING
1362.3ms  hmr-reload            重新加载了 1 个：['index.js']
1362.3ms  status     greeter    UNLOADING → DISPOSED
1362.4ms  report     greeter    我跑起来了  {"版本": "2.0.0", "招呼语": "晚上好", "入口": "第二版"}
1362.4ms  status     greeter    LOADING → ACTIVE

进程 pid：126252 → 126252

插件只多说了一次话，三个字段整整齐齐都是新版；进程 pid 一动没动。 换版本走的是热重载那条路——旧的拆掉、新的挂上，都在同一条事件流里。

这次换版本里，别的条目怎么样了
timer          没动
hmr            没动
lab-recorder   没动
greeter        走了一次 DISPOSED，重建一次

放大看

拆和建，全在 0.4 毫秒里

把 1362.0 ms 到 1362.4 ms 这段拉开——跟第 5 项一样，旧的还没拆完，新的已经开始建了。

↑ 黄色那段是新旧并存的窗口
旧的那个在拆 新的在建 新的就绪

顺序是：旧的先进入拆除，新的紧接着开始建，hmr 这时才报「重新加载了」， 旧的随即拆完，新的开口说话。

两处容易读错

一条「文件变了」，一条「重新加载」

只有 package.json 冒了一条「文件变了」
1235.7ms  hmr-change   文件变了：package.json
三个 .js 一条都没有

那三个文件已经在模块缓存里，直接进了这一批重新加载。 「文件变了」这个事件只发给变了但不在缓存里的文件。 所以形态是 1 条 change ＋ 1 条 reload，不是 4 条。

「重新加载了 1 个」不等于只换了一个文件
1362.3ms  hmr-reload   重新加载了 1 个：['index.js']
另外三个文件的新内容照样进来了

重新加载的单位是包的入口。入口一重导，它整棵依赖下去的缓存全被清掉重来， 另两个文件自然跟着换。证据就在插件说的那句话里——三个字段全是新版。

为什么四个文件只算一次

攒一会儿再动手：debounce

文件一变，hmr 先攒着，攒到这么多毫秒没有新动静了才真去重新加载。 checkout 落四个文件只要几毫秒，默认的 100 毫秒足够把它们收成一批。 把窗口拉到十倍再跑一遍，次数还是一次，只是整体推迟了将近一秒。

debounce 100 mscheckout 落完盘之后 111 ms 才重新加载
重新加载次数：1 · 插件说的：1.0.0 / 早上好 / 第一版 → 2.0.0 / 晚上好 / 第二版
debounce 1000 mscheckout 落完盘之后 995 ms 才重新加载
重新加载次数：1 · 插件说的：1.0.0 / 早上好 / 第一版 → 2.0.0 / 晚上好 / 第二版

一次 checkout ＝ 一次重新加载，跟窗口开多大无关；窗口只决定「等多久才动手」。 两档跑下来都没出现半截状态：每一次说的三个字段都来自同一版。

两档都在插件说满两次之后又固定等了 8 秒——验「不该再有第二次」不能靠轮询提前退出。

这一步的坑

盯 profile 目录外面的东西，得自己写 ignored

工作副本天然不在 profile 目录里面，所以 hmr 那条要写两个键： root 指向那个副本（不写就盯不到），ignored 也必须明写。

profile 那份 patch 里的 hmr 条目
- id: hmr
  name: '…'
  config:
    root: ['…/out/testhome/ch2_worktree/pinned-b']   # 那个钉住的副本
    ignored: ['**/node_modules']                     # 不写这行，整件事静默失灵
    debounce: 100

机制是这样：hmr 判断一个文件要不要忽略，看的是它相对 profile 目录的那条路径。 副本在 profile 目录外面，那条路径以 .. 开头—— 而 Windows 上它整条都不含 /，于是默认忽略名单里的 **/.* 退化成「以点开头就忽略」，把整个副本连人带马吃掉。

Windows
"..\\..\\pinned-b\\index.js"
   → 被忽略
POSIX
"../../pinned-b/index.js"
   → 不被忽略

症状是完全静默：不重载、不报错，插件一声不吭，日志里什么都没有。 名单里去掉 **/.* 这一条（明写成 ignored: ['**/node_modules']）， 副本里的文件才看得见。

把跟着 HEAD 的副本改成一团糟，这边纹丝不动
