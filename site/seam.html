独立专题 · 不属于教学线的任何一章

让别人能往你这儿挂东西

前面每一步，你写的插件都在用别人提供的东西。这份报告讲反过来那件事： 你自己提供一个，让别的插件来用——以及当两个人想提供同一样东西时会发生什么。

4 项 · 11 个用例 · 全套约 35 秒 · 都不需要 web
experiments/seam_provide_a_service · seam_one_owner · seam_registry · seam_who_decides

先说清楚

一项能力有三个角色

01
声明的一方 占住一个名字，规定这项能力长什么样
02
实现的一方 把活干出来
03
使用的一方 inject 那个名字，调它

三个齐了才叫一项能力。DSH 管这个整体叫 seam，并且明确规定 单独任何一角都不是 seam。这份报告只管前两角怎么写。

01提供一个服务 — 第一次站到另一侧
02一个名字一个主人 — 两个人想占同一个名字
03别让它们争名字 — 想让多个实现并存怎么办
04谁说了算 — 前三项看到的差别，根子在哪

01

提供一个服务

提供有两种写法。先把它们并排放着——做的事完全一样，都是把一个能被 inject 到的东西挂到 labSomething 这个名字上。

写法甲 · 裸对象
const 服务 = {
  你看得见谁() {
    return this.ctx?.fiber
      ?.entry?.options?.id;
  },
  ctx,
};

ctx.provide("labBare", 服务);
写法乙 · 服务基类
class 我的服务 extends Service {
  constructor(ctx) {
    super(ctx, "labKlass");
  }
  你看得见谁() {
    return this.ctx?.fiber
      ?.entry?.options?.id;
  }
}
new 我的服务(ctx);

注意两件事：方法体一字不差；两边都自己存了一份 ctx。 所以答案要是不同，差别就只可能来自框架交接服务的方式。

使用方那侧看不出区别

一个使用方同时 inject 两个，向它们问同一个问题： 「此刻你手上那份 ctx 属于谁？」

使用方写出来的见证文件 · witness-who.json
{
  "我是": "使用方",
  "裸对象":   { "写法": "裸对象",   "它看见谁": "裸提供方" },
  "服务基类": { "写法": "服务基类", "它看见谁": "使用方" }
}

裸对象报出的是它自己；服务基类报出的是调用它的那个条目。

框架把服务交到调用方手上时，会把方法里的那份 ctx 换成调用方的。 裸对象没有这个待遇，它手上永远是自己 apply 时拿到的那份。 这就是「继承服务基类」换来的东西——知道谁在调我。

这条是第 03 项的地基：往一张表里塞东西时，要把表项的寿命挂到塞它的那个插件身上， 前提就是能认出塞它的是谁。

02

一个名字一个主人

两个插件都想占 labSeat 这个名字，会怎样？

启动日志（退出码 1）
Error: dsh: plugin tree failed to load: failed to apply loader entry include (cordis:include):
failed to apply loader entry 裸乙 (./bare-owner.mjs):
service "labSeat" has been registered at <Include>
两边各走过什么状态
先到的 LOADING→ ACTIVE→ UNLOADING→ DISPOSED
后到的 LOADING→ UNLOADING→ FAILED | ACTIVE 从没出现过

后到的那个，provide 之后的代码一行都没执行。 而先到的那个虽然占上了、也跑到了 ACTIVE， 最后照样被拆掉——启动期一条失败，整树陪葬。

换成服务基类，还是抢不到

把其中一个换成写法乙，再撞一次。报错文本一字不差： 

// 两个裸对象相撞
service "labSeat" has been registered at <Include>

// 裸对象 vs 服务基类相撞
service "labSeat" has been registered at <Include>

独占不是「服务基类」那种写法的特性。 两种写法最终都落到框架那唯一一条注册通道上，重复检查就长在那条通道里—— 所以谁能占名只跟名字有关，跟写法无关。

对照实验坐实了病因：同样两个插件、同样两种写法，只把名字改成 labSeatA / labSeatB，两个都跑到 ACTIVE、实例照常活着。

排错提醒：报错点得出「谁失败了」，点不出「谁先占的」。 失败方的条目 id 和 name 都在（裸乙 (./bare-owner.mjs)）， 照着能在 patch 文件里找到那一行；但先占者只显示成 <Include>——那是 fiber 名， 不是条目 id。想知道先占者，去事件流里找那条「服务出现」，它带着条目 id。

03

别让它们争名字

既然一个名字只能有一个主人，那想让多个实现并存怎么办？ 办法不是去打破那条规矩，是绕开它：只让一个插件占名字，别人往它肚子里的表塞。 从头到尾没人跟谁争。

名册 · 声明的那一方
class 名册 extends Service {
  constructor(ctx) { super(ctx, "labRoster"); this.表 = new Map(); }

  register(id, 值) {
    const 表 = this.表;
    // this.ctx 属于调用方 —— 所以这个 effect 挂在塞东西的那个插件身上
    return this.ctx.effect(function* () {
      表.set(id, 值);
      yield () => 表.delete(id);
    });
  }
}

两个注册方并存，谁也不撞谁

使用方每 300 毫秒把表内容报进事件流，所以表的变化直接读得出来： 

   4.5ms  贡献甲   我往名册里塞了「贡献甲」  塞完表里有 ["贡献甲"]
   4.6ms  贡献乙   我往名册里塞了「贡献乙」  塞完表里有 ["贡献乙","贡献甲"]
   5.7ms  使用方   表里现在有  ["贡献乙","贡献甲"]
   6.5ms  贡献甲   LOADING → ACTIVE
   6.6ms  贡献乙   LOADING → ACTIVE
   6.6ms  使用方   LOADING → ACTIVE

对照第 02 项：那边两个插件抢同一个名字，一个当场失败、整个实例陪葬； 这边两个插件往同一张表里塞，两个都活。

表是空的，使用方照样活

把注册方全撤掉，只剩名册和使用方： 

{"我是": "使用方", "apply时表里": []}
使用方走过：LOADING → ACTIVE      实例照常活着

这是注册表式跟独占式最要紧的一处分别。 独占式的提供方缺席等于名字没人占，使用方 inject 不到就停在 PENDING、 启动期还会拖垮整个实例；这边名字有人占着（名册自己），空表不构成任何错误—— 失败推迟到真正去用表里的东西那一刻。

注册方下线，只少它那一行

实例跑着的时候把「贡献乙」禁用掉（改活层，热重放），同时看两件事：

该变的变了，不该变的没变
谁改动前改动后
表内容["贡献乙","贡献甲"]["贡献甲"]
贡献乙LOADING → ACTIVE…→ UNLOADING → DISPOSED
名册LOADING → ACTIVELOADING → ACTIVE 一个字没多
使用方LOADING → ACTIVELOADING → ACTIVE 一个字没多

表项的寿命跟着塞它的那个插件走，不跟着名册走。 靠的正是第 01 项那条：register() 里那句 this.ctx.effect(...)， this.ctx 属于调用方，所以 effect 挂在注册方的 fiber 上——它下线， 它那一行自己就没了，名册不用管。

观测手法：该变的（表少一行）用轮询等，不该变的（名册与使用方的状态序列） 用改动前后两次快照对比。两个判定用的手段不同，因为「验证发生了」和「验证没发生」 本来就不是同一种等法。

04

谁说了算

前三项读下来很容易得出一个印象：独占式的提供方缺席，使用方卡住、整个实例陪葬； 注册表式的表空着，使用方照样活。好像命运是由「怎么安排多个实现」决定的。

这一项拆穿它。三个用例共用同一个使用方文件、一个字都不改，换的只是对面那份名册； 而两份名册之间只差一个方法：

严格版比宽松版多出来的全部内容
[Service.check]() { return this.表.size > 0 }
// 框架在决定「等着这个服务的插件能不能开跑」之前会问一次，答否就当它不在
三次运行，使用方那个文件全程没改过
名册表使用方实例
严格版
有判据		 空 卡在 PENDING，apply 一次没跑 起不来，退出码 1
严格版
有判据		 有一行 LOADING → ACTIVE 活
宽松版
无判据		 空 LOADING → ACTIVE，拿到空表 活

第一行和第三行的表同样是空的，使用方同样一个字没改—— 差别只在名册那边多写／少写一个方法。第一行里名册自己还是 ACTIVE 的： 卡住使用方的不是「名册没起来」。

「独占还是注册表」不决定使用方的命运，那一刻的可用性判据才决定。 前三项看到的所有差别，根子都在这儿。

但判据造成的 PENDING，日志不告诉你在等谁

两种 PENDING 的判词不一样，而且是往难查的方向不一样： 

// 压根没人提供这个名字 —— 点得出名字
./locked.mjs: pending (waiting for service: 开锁服务)

// 有人占着，判据说不可用 —— 点不出名字
./roster-user.mjs: pending (waiting for services: unknown)

看到 waiting for services: unknown 时，方向不是「去找谁没提供这个服务」， 而是「去找哪个服务的可用性判据正在返回否」。 名字确实被占着，启动期审计那一侧看不出缺的是谁。

判词前半截打的是条目的 name（./roster-user.mjs）而不是 id—— 排错时拿 name 回 patch 文件里找。

收口

四项合起来是一句话

一条铁律一个名字只有一个主人，第二个来占的当场失败。跟你用哪种写法无关。
一个绕法想让多个实现并存，就别让它们争名字——只让一个占名，其余住进它的表里。
一个开关使用方能不能开跑，由服务那一刻的可用性判据说了算，两种安排都能挂。

继承服务基类换来的不是「独占」——那是所有写法都有的。 换来的是知道谁在调我，而整个注册表式的安排都架在这一条上。
