L0 · entry tree 长什么样

你写了一份 config，框架照着它把插件挂起来。 但进程里真正跑着的那棵 entry tree，跟你写的 config 不是一回事——这一课把差别指给你看。

这一课用到的词，一律用源码与官方文档里的原词

entry
树上的一个节点，一个被挂载的插件实例。字段只有 id / name / config / disabled / group / inject 六个
row
patch 文件里的一行。它是 entry 的来源，不是 entry 本身——「Later layers win per row」
effective config
各 layer 叠完之后算出来的那份配置。--dump-config 打印的就是它
empty root
cordis.yml 里那个 []，所有 layer 都叠在它之上
layer
四种：bundle patch、profile 的 cordis.patch.yml、home 级、--patch overlay
subtree
include 底下那一层。config 里的每个 row 都变成这里的一个 entry
root group
树的最外层，include 自己住在这。热重放碰不到这一层

这是「先总后分」的总。后面六个部分各展开其中一块，这里只求你记住整棵 tree 的形状。

这一课立住的五条

每条后面都有专属的一课深入，这里只给结论和它的边界。

effective config ≠ entry tree

树上比 --dump-config 多一个 cordis:include。 这个差别是结构性的、跟你怎么写 config 无关：整份 effective config 就装在它的 config.patches 里，它要是出现在自己装的那份 config 中才叫自指。

展开于 L7 · include 与 config.patches

层级：谁在 subtree 里，谁不在

config 里的每个 row 都变成 include subtree 里的一个 entry； include 自己在 root group。热重放只重新组合 subtree—— 这条决定了「改 hmr 的 config 会不会把它自己重挂掉」。

展开于 L8 · 层级

「不叠 bundle」不等于「什么都没有」

基线不叠任何 bundle，是为了去掉 dsh-base 那 78 个 entry 的噪声 ——其中只有 timer 和 hmr 跟插件系统本身有关。 那两个要自己显式带上：真实部署里它们一直在，减噪不等于模拟一个它们不存在的世界。

基线：make_minimal_profile()

boot 期 PENDING 无条件致命

依赖等不到的 entry 会让整个进程以退出码 1 退出。审计只在 boot 期做一次， 跟叠了哪些 bundle 无关。

展开于 L11 · boot 审计

hmr 的 root 决定它监听什么

基线默认给的是空数组——够监听 patch 文件（那是按精确路径注册的，与 root 无关）， 但不监听任何代码文件。所以默认形态下：改 patch 会热重放，改插件源码不会热重载。 要测热重载就给 hmr_root 传一个真的目录。

展开于 L15 · 代码热重载
