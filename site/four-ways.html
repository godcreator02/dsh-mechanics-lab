四种交付途径

第一章教出来的插件是 profile 目录里的一个文件——那不是能给别人的东西。 同一个插件换四种挂法：挂出来的条目一模一样，要付的代价差得很远。

uv run pytest experiments/ch2_four_ways/ -n 0 -s · 3 个用例 · 约 39 秒

四条路

同一个包，四种挂法

这个包一共三个文件：index.mjs、package.json、 还有一份包自己带的 patch 文件。四条路上跑的插件源码一个字节都不差—— 途径① 拷进 profile 目录的，就是这个包里的 index.mjs 本尊。

① 单文件

把那个 .mjs 扔进 profile 目录，自己在 patch 文件里写一条 insert。

条目上的 name：./courier.mjs

② 目录链接

在 node_modules 里建一条指向包目录的链接，dependencies 里补一行声明，patch 文件里自己写 insert。

条目上的 name：ch2-courier

③ 正经安装

跑官方命令 dsh plugin --profile <名> add <包目录>，patch 文件里一个字都不写。

条目上的 name：ch2-courier

④ 工作副本

跟途径② 同一套写法，只是链接指向一份 git 工作副本（worktree），而不是仓库本体。

条目上的 name：ch2-courier

四条路各起一个实例，一条路一个 profile，互不干扰。下面所有对照都出自这四次运行。

条目身上不带「我是怎么被挂上来的」这种标记。 状态怎么走、apply 跑在什么时候、config 收到了什么、 disabled 是什么——四条路没有任何区别。树上看不出来，插件自己也看不出来。

表里唯一那一格黄的，是 name 写路径还是写包名。 那是你自己写的那一行，不是框架给条目盖的章：途径③ 那行写在包自带的 patch 文件里， 照样是人写的。config 那一行也一样，四份各不相同是因为四份就那么写的。

结论二

差别全在 profile 目录留下的痕迹上

实例跑过一轮之后，什么都不挂的 profile 目录里是这三样（node_modules 另算）： cordis.patch.yml、cordis.yml、package.json。 四条路各自往上加了什么，一条一条看。

四条路里只有③ 免了你手写 insert，代价是它在 profile 目录里留下的东西最多—— 多一个锁文件、多三样 pnpm 自己的内部条目，还改了 package.json 里 dsh.profile.bundles 这个键。其余三条谁都没碰过那个键。

②④ 的痕迹逐项相同——它们本来就是同一套写法，区别只在链接指向哪个目录。 对 DSH 来说「那头是不是 git 工作副本」根本不是它关心的事。

那条命令改了什么

package.json 执行前后，原样摆一起

profile 的 package.json：执行前
{
  "name": "dsh-profile-manifest",
  "private": true,
  "dsh": {
    "profile": {
      "bundles": []
    }
  },
  "dependencies": {
    "lab-recorder": "link:D:/…/observatory/lab-recorder"
  }
}
profile 的 package.json：执行后
{
  "name": "dsh-profile-manifest",
  "private": true,
  "dsh": {
    "profile": {
      "bundles": [
        "ch2-courier"
      ]
    }
  },
  "dependencies": {
    "ch2-courier": "link:D:/…/fixtures/courier",
    "lab-recorder": "link:D:/…/observatory/lab-recorder"
  }
}

两处：dependencies 多一行，dsh.profile.bundles 这个键的名单里多一个包名。 第二处是四条路里独一份的——它就是这条命令替你办的那件事。

这个键为什么会让条目出现、它跟你手写的那条有什么不一样，是下一项的事，这里先记住 「有这么一个键、装的时候被改了」。

命令回显（退出码 0）
dsh plugin --profile manifest add <包目录>

  | Already up to date
  | dependencies:
  | + ch2-courier 1.0.0 <- ..\..\..\..\..\experiments\ch2_four_ways\fixtures\courier
  | Done in 402ms using pnpm v11.21.0

profile 目录：执行前 ['cordis.patch.yml', 'node_modules', 'package.json']， 执行后多一个 pnpm-lock.yaml。patch 文件从头到尾一个字没变—— 这条命令不写 insert，也不替你写。

它只动了 profile 目录，插件源码目录一个字节都没写。 那边既没多出 node_modules，也没多出锁文件。 全程也不上网：传进去的是本地路径，记下来的依赖是一条 link:，没有任何东西要从远处拉。

包能自注册，靠的是什么

包摆在那儿不装，什么都不会发生

途径③ 之所以不用手写 insert，是因为这个包自己带了一份 patch 文件， package.json 里用 dsh.bundle.patch 指向它。 那么问题来了：让条目出现的，是「包目录里躺着这份文件」，还是「装」这个动作？

对照组：链接建好了，patch 文件也在包根躺着，就是没跑那条安装命令
实例还活着？    True
树上的条目：    ['hmr', 'include', 'lab-recorder', 'timer']
它说的话：      （一句都没有）
那份名单：      dsh.profile.bundles = []
包链接进去了 · patch 文件就在包根 · 树上一个 courier 都没有

自注册靠的是「装」这个动作把包名写进那个键，不是「包目录里有那份文件」。 文件躺在那儿，没人会去读它。

实例照常活着——少挂一个插件不是错误，也没有任何提示。 跟第 7 项那个「id 打错全程静默」是同一副脾气：没生效的时候，你得自己回去确认。

用途径③ 要当心的三处

都不报错，所以都得自己盯

相对路径会重锚
包目录那个参数是按你敲命令时所在的目录算的。 换个目录敲同一条命令，算出来的就是另一个地方。
→ 传绝对路径，就没有「算到哪去了」这个问题
profile 名打错不报错
--profile 后面写错一个字母，它不会说「没这个 profile」， 而是新建一个然后把包装进去。
→ 装完回去看一眼是不是装到了你要的那个 profile
回显跟落盘的不是一个东西
回显打的是相对路径 ..\..\..\..\..\experiments\…\courier， 写进 package.json 的却是绝对路径 link:D:/…/fixtures/courier。
→ 要核对装了什么，看 package.json，别看回显

另外那句 Already up to date 是 pnpm 的口头禅，跟这次装没装上无关—— 以 package.json 和 node_modules 里的实际情况为准。

怎么选

结果既然一样，就只挑代价

四条路挂出来的条目 完全一样　·　差的只有你要付的东西
① 单文件 自己试一个想法。一个文件、拷进去、写条 insert 就完事—— 但这份东西只存在于这个 profile 目录里，给不了别人。
② 目录链接 已经做成包了，但还在自己机器上改。 源码在哪就在哪改，profile 目录里干干净净不留文件。
③ 正经安装 要交给别人用。对方只需敲一条命令，不用被告知「还得去 patch 文件里写一条」—— 代价是它会改 profile 的 package.json，还留下锁文件和一堆 pnpm 内部文件。
④ 工作副本 要钉在某个版本上。写法跟② 完全一样，只是链接指向一份钉住的 git 工作副本。 钉在哪、换版本会怎样，是第 11 项的事。
