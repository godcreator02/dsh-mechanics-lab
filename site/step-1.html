最小实例与那台仪器

一个 DSH 实例能瘦到什么程度？顺便把后面每一步都要用的那只眼睛装上—— 它是树上的一条，不是外挂的探针。

uv run pytest experiments/step1_run_an_instance/ -n 0 -s · 2 个用例 · 约 5 秒

先说仪器

它凭什么能看见

要看清插件加载时发生了什么，得有个东西在进程里听着。这台采集器叫 lab-recorder，它本身就是一个普通插件条目——写在同一个 patch 文件里， 跟被观测的东西平级，没有任何特权。所以后面每张图里你都会看到它。

它怎么听见框架说话

// fiber 每次状态变化触发一次，带旧状态。
// 这是抓住 LOADING 这种几毫秒窄窗口的唯一办法 —— 轮询必然错过。
ctx.on("internal/status", (fiber, oldValue) => {
  push("status", {
    id:   fiber.entry?.options?.id,
    from: FIBER_STATE[oldValue],
    to:   FIBER_STATE[fiber.state],
  });
});

FIBER_STATE 那张数字→名字的表得手写死在代码里：它在 cordis 里是 TypeScript 的 const enum，编译后被内联成数字字面量， 运行时根本不存在这个对象，import 不到。

它怎么让别的插件也能说话

// 框架事件只回答「框架对这个条目做了什么」，
// 回答不了「这个插件自己拿到了什么」—— 那只有插件自己知道。
ctx.provide("labObserver", {
  // 传一次自己的 ctx，采集器反查你在树上的 id ——
  // 比让插件自报名字可靠：它写死的名字未必等于条目 id
  for(callerCtx) {
    const who = whoOf(callerCtx);
    return (note, data) => push("report", { who, note, data });
  },
});

于是「插件说的」和「框架说的」进同一条流、共用一套时间轴——先后关系直接读得出来， 不用去拼两份数据。从第 2 步起，每个插件都会用到它。

它的能力上限：拿不到自己挂载之前的历史。 采集器自己也要被加载，在它 apply 之前发生的事没人记——所以事件流第一批是 snapshot（睁眼时看到的样子），那之前的过程是丢的。 下面所有毫秒数都相对它睁眼那一刻，不是进程启动。

这一步

一个实例最少需要什么

只写 timer 和 hmr 两条。加上采集器，再算上框架自己放的树根， 一共四条——这是能瘦到的极限。

现场

假 home 的全部内容
out/testhome/step1/
├─ profiles/
│  ├─ node_modules/   252 条，dsh 自建
│  └─ minimal/
│     ├─ package.json
│     ├─ cordis.patch.yml
│     ├─ cordis.yml       dsh 写的
│     └─ node_modules/
│        └─ lab-recorder → link
├─ logs/
└─ events.jsonl        采集器写的

绿色是我们放的，灰色是 dsh 生成的。 上一层那个 252 条的 node_modules 是 dsh 维护的链接农场—— timer / hmr 写包名能被找到就靠它，不用手工装。

profiles/minimal/package.json
{
  "name": "dsh-profile-minimal",
  "private": true,
  "dsh": { "profile": { "bundles": [] } },
  "dependencies": {
    "lab-recorder": "link:…/observatory/lab-recorder"
  }
}
profiles/minimal/cordis.patch.yml — 组合就写在这
# 一个实例最少需要的两条
- insert:
    - id: timer
      name: '@deepseek-ai/cordis-plugin-timer'

    - id: hmr
      name: '@deepseek-ai/cordis-plugin-hmr'

# 仪器，独立一块 —— YAML 数组允许多个 insert 块
- insert:
    - id: lab-recorder
      name: lab-recorder
      config:
        out: "…/out/testhome/step1/events.jsonl"
        flushMs: 100
profiles/minimal/cordis.yml — dsh 每次启动重写，别改它
# dsh profile root — an empty entry list. The tree is composed
# as patches: … Edit cordis.patch.yml, not this file.
[]

跑出来

PENDING 等依赖 LOADING 正在跑 apply ACTIVE 就绪 仪器
timer 变 ACTIVE
1.8 ms
hmr 才开始 LOADING
1.9 ms
hmr 加载耗时
12.6 ms（1.9 → 14.5）—— 四条里最慢的

hmr 一直在 PENDING 等着，直到 timer 变成 ACTIVE 才开始加载。 顺序不是 patch 里的书写顺序决定的，是依赖决定的。

把 timer 那两行删掉再跑一次，实例根本起不来，退出码 1，日志点名： 

@deepseek-ai/cordis-plugin-hmr: pending (waiting for service: timer)

这两条是捆绑的。至于「等一个不来的服务」到底意味着什么，第 9 步会拆开讲。
