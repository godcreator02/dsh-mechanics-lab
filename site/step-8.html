第 8 步 / 共 9 步

改别人已经挂上的条目

前七步一直在写 - insert:。上一步撞了车才发现：再 insert 一遍同一个 id 不是「改」，是「多一条」，而且直接把实例弄挂。真要改，得换个写法。

uv run pytest experiments/step8_change_an_existing_entry/ -n 0 -s · 4 个用例 · 约 19 秒

两种写法

差别只在有没有 insert

- insert: 底下的 → 加一条新的
顶格写 - id: xxx → 改已经有的那一条
同一个 patch 文件，先加后改
# 先挂上
- insert:
    - id: speaker
      name: ./speaker.mjs
      config:
        台词: 原来的台词
        音量: 3

# 再改它 —— 顶格，不在 insert 底下
- id: speaker
  config:
    台词: 改过的台词
插件实际收到 
{"台词": "改过的台词"}
←
原来那份 
{"台词": "原来的台词",
 "音量": 3}

音量: 3 没了——覆盖是把整个 config 换掉，不是把新键并进旧的里面。 只想改一个键，也得把要保留的键全部重写一遍。

另外 speaker 全程只说了 一句——覆盖不会变成两份，它自始至终是同一条。

写错 id 会怎样

什么都不会发生，而且什么都不会说

- insert:
    - id: speaker
      name: ./speaker.mjs

- id: speakr          # 打错一个字母
  config:
    台词: 改不到

- id: speaker         # 后面这条照样生效
  config:
    台词: 后面这条照样生效
实例照常活着 · speakr 从没成为条目 · 后面那条正常生效
启动日志：一个字都没有

不要指望框架提醒你。 改一个不存在的 id，既不报错也不警告——那一段就像没写过一样被跳过， 你只会发现「怎么没改上」，却拿不到任何线索。

这跟第 3 步那个坑是同一类：config 键名拼错也是全程静默。 DSH 在「你写错了」这类场合普遍不吭声——所以改完一定要回去确认真的改上了。

再 insert 一遍呢

跟上一步撞车是同一个死法

- insert:
    - id: speaker
      name: ./speaker.mjs

- insert:
    - id: speaker      # 又来一条同名的
      name: ./speaker.mjs
启动日志（退出码 1）
Error: dsh: plugin tree failed to load:
  failed to apply loader entry include (cordis:include):
  duplicate loader entry id: speaker

不是后面盖前面，也不是两份一起跑——实例根本起不来。 第 7 步「两处各写一条同 id」和这里「同一处写两遍」，撞的是同一堵墙： 树上不允许出现两个一样的 id。

还能改什么

比如把别人挂上的那条关掉

# 前面那条原样留着，一个字不动
- insert:
    - id: speaker
      name: ./speaker.mjs

# 后面这条说了算
- id: speaker
  disabled: true

实例照常活着，speaker 在树上，但一句话都没说——第 4 步那个开关， 现在可以隔着距离拨了。

这就是「改已有条目」真正有用的地方：你不用去动别人写的那一段， 在自己这边追加一条，就能改掉它的 config、关掉它、或者调整它的其它字段。
