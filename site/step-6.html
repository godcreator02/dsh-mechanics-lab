改了代码立刻生效

第 1 步照抄的那两条里，hmr 一直没解释过。它盯着文件——你存一下， 被改的那个插件就自己重来一遍，实例不用重启。

uv run pytest experiments/step6_hot_reload/ -n 0 -s · 5 个用例 · 约 50 秒

做了什么

就是在编辑器里改一行

greeter.mjs — 把「第一版」改成「第二版」，存盘
export const inject = ["labObserver"];

export function apply(ctx, config) {
  const say = ctx.labObserver.for(ctx);
  say("我跑起来了", { 版本: "第一版" });   → 改成「第二版」
}
插件说过的话（读自事件流）
2.3 ms
我跑起来了 {"版本": "第一版"}
1507.1 ms
我跑起来了 {"版本": "第二版"}

进程从头到尾没重启——同一个实例、同一条事件流，插件说了两次话， 第二次带的是新代码里的内容。

放大看

整个换代过程只有 700 微秒

把 1506.5 ms 到 1507.3 ms 这段拉开——注意旧的还没拆完，新的已经开始建了。

↑ 黄色那段是新旧并存的窗口
旧的那个在拆 新的在建 新的就绪

顺序是：旧的先进入拆除，新的紧接着开始建，然后 hmr 才报「重新加载了 greeter.mjs」， 旧的这时才真正拆完。 不是「拆干净再建」——两个在时间线上有重叠。

同一次热重载里，别的条目怎么样了
timer          没动
hmr            没动
lab-recorder   没动
greeter        拆了一次，重建一次

只有被改的那个重来。其余条目一次都没被拆过——所以观察器能一路记录全程， 没有因为自己被重启而断片。

root 决定盯哪儿

五种配法，实测结果

root: ['.']
✓
. 指的是 profile 目录——插件就放在那儿
不写 config
✓
默认就是 ['.']，跟上面那条效果一样
root: ['D:/…/profiles/xxx']
✓
绝对路径也行，跟 '.' 等价
root: ['./elsewhere']
✗
盯的是 profile 里另一个目录，插件文件改了毫无反应
root: []
✗
明写着一个目录都不盯

所以第 1 步那个实例其实早就能热重载了——那条 hmr 没写 config， 吃的是默认值 ['.']。这一步只是把这件事摆到明面上。

两条「不生效」的都是固定等 15 秒之后才判的——验「什么都不该发生」不能轮询提前退出， 提前退出只能证明「此刻还没发生」。

出错了往哪看

这一步不能指望日志

hmr 那几行 watching … / reload plugin at … 是 info 级日志， 而这个最小实例里没有装任何把日志打到控制台的东西——两份日志文件都是 0 字节。

判断「到底重载了没有」，看的是插件有没有第二次说话，不是看日志。 这也是把观察器做成底层依赖的好处之一：插件自己开口，比等框架打日志可靠。
