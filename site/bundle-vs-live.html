有一份 patch 文件，改了没反应

前面每次改 patch 文件，一两秒就生效。第 9 项那种「正经安装」进来的插件， 它的条目也写在一份 patch 文件里——但那一份你改了，实例当没看见。

uv run pytest experiments/ch2_bundle_vs_live/ -n 0 -s · 3 个用例 · 约 23 秒

先给两边起个名字

你一直在改的那个，从现在起叫「活层」

到这里为止，「写 patch 的地方」见过两处：profile 目录里那份、home 目录里那份（第 6 项）。 它们是同一种东西，合起来叫活层——不是新冒出来的概念， 就是你前面每一次动手改的那个文件。

这一项补上第三处：包里那份，叫 bundle 层。它不在你手上，跟着包走。

包能自注册

profile 那份 patch 里一个字都没提它

这一项的教学插件 ch2-greeter 自己就是一个包。它比第 9 项那种包多带两样东西：

package.json — 多了 dsh.bundle.patch 这一段
{
  "name": "ch2-greeter",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "main": "index.js",
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
包根目录/cordis.patch.yml — 上面那一段指着的就是它
# 这份 patch 文件跟着**包**走 —— 它住在包里，不在 profile 目录里。
# package.json 的 dsh.bundle.patch 指着它，包一旦进了某个 profile 的 bundle
# 名单，这里写的条目就自动上树，profile 那边一个字都不用写。
- insert:
    - id: greeter
      name: ch2-greeter
      config:
        版本: 第一版

然后我们做的唯一一件事，是把包名写进 profile 的 bundles 名单：

profiles/selfmount/package.jsonbundle 名单 ＋ 依赖
"dsh": {
  "profile": {
    "bundles": ["ch2-greeter"]
  }
},
"dependencies": {
  "lab-recorder": "link:…",
  "ch2-greeter": "link:…"
}
profiles/selfmount/cordis.patch.yml活层——没有 greeter
- insert:

↓ 起实例 ↓
树上：include   greeter   timer   hmr   lab-recorder

    2.7ms  report   greeter   我跑起来了  {"版本": "第一版"}

没人替它写 insert，它自己带来的。 条目上了树、apply 跑了、config 也收到了——收到的正是包里那份 patch 写的「第一版」。

注意 package.json 里是两件事：进 bundles 名单和装进这个 profile （依赖声明一行 ＋ node_modules 里一条链接，第 9 项那套）。少了后者， name: ch2-greeter 根本找不到东西。

主证据

同一时刻，两份文件各改一处

同一个实例上挂着同一个插件的两个条目——一个来自 bundle 层，一个来自活层。 两边的 config 里都写着一个「版本」，插件跑起来就把自己收到的那一版报出来。

包根目录/cordis.patch.ymlbundle 层
- insert:
    - id: greeter
      name: ch2-greeter
      config:
        版本: 第一版  → 改成「第二版」
profiles/coldhot/cordis.patch.yml活层
- insert:
    - id: greeter-live
      name: ch2-greeter
      config:
        版本: 活层第一版  → 改成「活层第二版」
↓ 两处同时存盘，然后固定等 15 秒 ↓
事件流（读自 events-coldhot-run1.jsonl）
    1.4ms  report   greeter        我跑起来了  {"版本": "第一版"}
    1.5ms  report   greeter-live   我跑起来了  {"版本": "活层第一版"}
  416.6ms  report   greeter-live   我跑起来了  {"版本": "活层第二版"}

—— 15 秒到了，再没有第四行 ——
greeter（bundle 层）
报过：['第一版']
跑起来：1 次
greeter-live（活层）
报过：['活层第一版', '活层第二版']
跑起来：2 次

同一个实例、同一条时间线、同一种改法，两种下场。 活层那条被拆了重来一遍，报出了新值；bundle 层那条从头到尾一声不吭， 还挂着启动时那个「第一版」。

「跑起来几次」比「报了几次话」更硬：报话是插件自己的事，跑起来几次是框架记的账。

「什么都没发生」怎么证

三个能想到的疑问，同一份事件流全堵死

是不是等得不够久
两条摆在同一条时间线上。活层那条在第 416.6 毫秒就已经重来完了， 而这一等等满了 15 秒——快了三十多倍的事都办完了，慢的那件根本不是「还没轮到」。
是不是没人盯着那个目录
这次 hmr 的 root 特意指着包所在的目录： …/pkg-coldhot，包就在里面。结果事件流里 hmr 报的动静是 0 条——目录被盯着，文件也确实改了，它就是没当回事。
是不是那次重来压根没波及它
恰恰相反。那一次重来把每一个条目都重新过了一遍， greeter 也在名单里——只是过它的时候，手里拿的还是启动时读到的那份内容。
那次重来的原始事件（seq 27–35，摘自同一份事件流）
416.4ms  status         greeter-live   ACTIVE → UNLOADING
416.5ms  status         greeter-live   UNLOADING → LOADING
416.6ms  report         greeter-live   我跑起来了  {"版本": "活层第二版"}
416.8ms  entry-dispose  greeter        legacy: {config: {"版本": "第一版"}}   ← 过了，但拿的是旧的
416.8ms  entry-dispose  timer          legacy: {…}
416.8ms  entry-dispose  hmr            legacy: {…}
416.9ms  entry-dispose  lab-recorder   legacy: {…}
416.9ms  status         greeter-live   LOADING → ACTIVE
416.9ms  entry-dispose  greeter-live   legacy: {config: {"版本": "活层第一版"}}

准确的说法不是「那次重来没波及它」，而是「重来确实把整套条目过了一遍， 但包里那份 patch 文件根本没被重新读一眼」。 实例手上那份内容，还是启动那一刻读进去的。

那什么时候才算数

重启一次，新进程重新读盘

什么都不再改，把实例停掉再拉起来——这一次它把包里那份 patch 文件重新读了一遍。

重启之后的事件流（读自 events-coldhot.jsonl）
    1.4ms  report   greeter        我跑起来了  {"版本": "第二版"}
    1.4ms  report   greeter-live   我跑起来了  {"版本": "活层第二版"}

改动一直都在，只是没人再读它。 bundle 层不是「改了不算数」，是「只在启动那一下算数」——实例活着的这段时间里， 它手上捏的是一张启动时拍下来的定格照。

撞车

两层写了同一个 id，实例起不来

包进了 bundles 名单，你又在活层 insert 了一个同名的 id：

bundle 层（包里那份）
- insert:
    - id: greeter
      name: ch2-greeter
      config:
        版本: 第一版
活层（profile 那份）
- insert:
    - id: greeter
      name: ch2-greeter
      config:
        版本: 活层写的
启动日志（退出码 1，插件一句话都没说过）
Error: dsh: plugin tree failed to load:
  failed to apply loader entry include (cordis:include):
  duplicate loader entry id: greeter

跟第 6 项撞的是同一堵墙。 两层也是拼起来的，同一个 id 出现两次就成了两个条目，挂载时查重，当场抛错。

差别只在于：这次撞车的一边在包里，那个 id 是写包的人定的，你未必知道。 在活层随手写一个同名的，撞得毫无征兆。要看它占了哪些 id， 只能去翻包根目录那份 cordis.patch.yml。

分水岭

一句话：谁热谁冷

你改了什么 实例的反应
活层
profile 那份 / home 那份		 一两秒后那个条目被拆了重来，进程不动
bundle 层
包根目录那份		 什么都不发生。要生效必须重启

这就是第 9 项那张表里「正经安装：必须重启」的全部原因—— 官方安装命令把包写进 bundles 名单，插件的条目就来自 bundle 层， 而 bundle 层是启动时定格的。

第 9 项还有一条路没这个毛病：依赖指向一个工作副本，条目一直待在活层， 换版本只是换那个副本指向哪儿。那是下一项的事。
