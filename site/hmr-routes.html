热重载的两条路

hmr 盯着文件，但它盯的不是一堆文件、走的也不是一条路。 代码走一条，配置走另一条，两条从入口到落地互不相干——只是恰好住在同一个插件里。

uv run pytest experiments/chx_hmr_across_junction/ -n 0 -s · 11 个用例 · 约 140 秒

整体

五层，从磁盘到重挂

往上每一层都只依赖下一层的产物。搞清楚一个现象归哪一层，比记住现象本身有用—— 「配置改了没生效」在第四层和第五层各有一个成因，它们会叠在一起。

1
磁盘布局node_modules 里有什么、指向哪。pnpm 摆现场，但真正找包的是 Node 的 parent-walk 解析
pnpm + Node
2
patch 文件声明树上有哪些条目、各自的 id 和 config。三种语义：追加、插进某个 group、按 id 覆盖
include
3
层的组合bundle 层（按名单序）→ profile 活层 → home 层 → --patch，依次叠到空根上，后来的按行胜出
applyEntryPatches
4
进程内的 composed四层全在内存。区别不在「进没进」，在重放时谁会重读盘
profile-boot
5
监听两条互不相干的路径：一条盯代码，一条只盯两个路径固定的配置文件
hmr

第五层特写

两个 watcher，配置正好相反

它们不是「一个 watcher 的两种模式」，是两套独立的 chokidar 实例，连排除规则的取向都相反。

盯代码

root watcher

盯什么
root 里列的目录，相对 base 解析
排除
有筛子 —— **/node_modules、**/.*、cache、data
初始扫描
忽略（ignoreInitial: true）
认哪些事件
只认 change。新建、删除对模块重载什么都不做
合并连改
真去抖，debounce 默认 100ms
失败
回滚：恢复缓存 + 重新注册旧插件
盯配置

registerConfig watcher ×2

盯什么
两个精确路径，跟 root 完全无关
<profile>/cordis.patch.yml
$DSH_HOME/cordis.patch.yml
排除
没有筛子（ignored: undefined）
初始扫描
算数 —— 注册时已存在的层必须 apply 一次
认哪些事件
add / change / unlink 都认
合并连改
不去抖，靠 dirty 标记串行：跑完发现又脏了就再跑一遍
失败
hmr 不做补偿——不需要：entry.update() 本身是事务性的，apply 失败整棵树一点不动。它只记 warn + 发 hmr/config-update-failed

「root: [] 就什么都不监听」是错的。 空 root 只关掉左边那个。改 patch 文件照样秒级生效——它走的是右边那条，按精确路径注册，跟 root 无关。

两条路互不相通。 左边换配置不换代码——重挂用的是缓存里那份模块；右边换代码不换配置——新代码拿到的是上一程那份 config。 所以同时改了代码和配方，拿到的是新代码配旧配方。

右边那条路能不能走通，归结为一个条件： watcher 报出的路径经 pathToFileURL 之后，要跟 loadCache 的 key 字节相同。 而 loadCache 的 key 永远是 realpath（Node 解析模块时就解了）， watcher 报的路径从不 realpath——它保持你给的入口形态，从那个入口爬出来的每条路径也一样。 所以 watch 的入口必须本身就是真实路径。 手填一条 junction 路径不行；在 profile 里建条链接指向外面的源码、让 chokidar 自己跟着爬进去， 也一样不行——两种方式 watcher 都出声，报的都是链接路径。

为什么

分界线不是「包 vs 用户」，是路径怎么来的

--patch 明明是用户在命令行给的，一样冷。真正决定冷热的是： 这一层的路径能不能在启动前算出来。

dsh/lib/profile-boot-*.js — 重放时到底重读了什么
const composeLive = () => structuredClone([
  ...composed.bundlePatches,                              ← 复用内存
  ...loadOptionalPatches(NAME, profile.patchPath) ?? [],  ← 重读盘
  ...loadOptionalPatches(NAME, homePatchPath()) ?? [],    ← 重读盘
  ...composed.overlays,                                   ← 复用内存
]);
层路径从哪来重放时
bundle 层 读 profile 的 package.json 拿 bundles 名单 → 逐个 resolveBundleDir → 各自 package.json 的 dsh.bundle.patch 冷
profile 活层约定死的：<profile 目录>/cordis.patch.yml热
home 层约定死的：$DSH_HOME/cordis.patch.yml热
--patchargv 给的冷

路径由约定固定、启动前就能算出来的才热，其余一律当启动期常量。 热重放 bundle 层等于要热重放整个 loadProfile()——名单变了怎么办、包被卸载了怎么办； 而活层就是读一个文件、解析一个 YAML 数组。复杂度差一个量级。

内存里那份 bundlePatches 装的是什么： 各 bundle 的 patch 文件解析后的条目数组，按名单顺序拍平成一个 JS 数组。 不是文件文本，也不是包的代码——包的代码走普通模块解析，跟 bundle 身份无关，所以它照样是热的。

谁能救

四格，两列的结论完全不同

两行是两种使用场景：自己开发插件，和装别人的插件。 「bundle 是冷的」这句话每次都要问一句冷的是什么——冷的是配方； 代码那一列，两种形态一模一样。

bundle 自注册 装别人的插件就是这个形态 —— 条目由包自己那份 patch 生，你不用写 dsh plugin add ./本地目录

两种冷不是一回事。 代码那半的冷是配置问题——watcher 的范围没罩住源码，改两个键就行。 bundle 配方那半的冷是代码问题：全仓库只有两个 registerConfig 调用点、都不是它， 而且就算给它注册了，composeLive() 里 bundlePatches 还是那个常量数组。 改配置够不着，得写插件。

落到手上

开发期该怎么摆

实测下来只有一件事真正决定代码热不热：watcher 的范围罩没罩住源码， 以及它报出的路径跟 loadCache 的 key 对不对得上。条目写在哪一层不影响。

常规做法

源码留在工作目录，改 hmr 两个键

root
加源码目录的真实路径。填 node_modules 里那条 junction 没用——watcher 报链接路径，loadCache 存真实路径
ignored
去掉 **/.*，其余三条要重述（patch 替换整个 config，不深度合并）
两个都要
只加 root 不改 ignored，watcher 一声不出、日志里没有任何提示——最难查的那种
代价
watch 范围里的 .git 不再被跳过，而它在每次 git 操作时疯狂变动；绝对路径写进 patch 也把机器路径钉死了
少见但最省事

源码摆进 profile 目录

怎么摆
源码放 <profile>/src/你的包/，node_modules 里的 junction 指过去
hmr
一个字都不用改。相对路径不以 .. 开头，撞不上任何一条排除规则
为什么少见
源码得住在 $DSH_HOME 底下，多数人的工作目录不在那儿

配方想热，就把条目写活层。 开发期别让包自注册——条目直接写 profile 的 cordis.patch.yml，这样代码和配方双热； 等要分发了再把它移进包里，那时候本来也不需要热重载了。

抄这段

hmr 到底怎么改

写在 profile 的 cordis.patch.yml 里。裸 - id: 是「按 id 覆盖已有条目」—— dsh-base 已经插了这一行，你在后面的层把它的 config 换掉。

$DSH_HOME\profiles\demo\cordis.patch.yml
- id: hmr
  name: '@deepseek-ai/cordis-plugin-hmr'
  config:
    root:
      - .
      - D:/work/hello-plugin        # 源码目录的真实路径，正斜杠
    ignored:
      - '**/node_modules'          # 默认名单里的三条，一条都不能漏
      - cache
      - data
      # '**/.*' —— 故意不写。就是它误伤了 ../ 开头的路径
    debounce: 100
三个必须

写错了不报错，只是静默失灵

真实路径
填源码目录本身，不是 node_modules/你的包 那条链接。填链接 watcher 会出声但不重载
重述三条
patch 替换整个 config、不深度合并。只写 ignored: [] 会把 node_modules 也放进 watch 范围
两个键一起
只加 root 不动 ignored，watcher 一声不出；只动 ignored 不加 root，范围压根没扩过去
验一下通没通

三个信号，分得出断在哪

没有日志
watcher 没看见——root 或 ignored 还不对
hmr/change
watcher 看见了但没人认领——多半是 root 填成了链接路径
hmr reload plugin at …
通了。这行是 hmr 自己打的，插件的行为也该跟着变

顺带一个撞车：进了 bundles 名单，活层又 insert 了同一个 id。 两层拼起来那是两个条目、id 撞了。 dsh plugin add 会自动把声明了 dsh.bundle 的包加进名单，所以这事很容易在你没察觉时发生。 换个 id 就合法：同一个包挂两次、各有各的 config； 这时改一次代码发一次 hmr/reload，但两个条目都会重来——重挂遍历的是一个 Plugin 的所有 fiber， 每个 fiber 各自沿用自己那份 config。

撞车的两种时机

启动时撞进程就没了，运行中撞会被兜住

同一个错误，发生在两个时刻，下场完全不同。差别不在错误本身， 在于有没有「上一个好状态」可以退回去。

启动时

进程当场退出

怎么发生
两层在 boot 时就拼出了重复的 id
结果
挂载期抛 duplicate loader entry id，进程退出，日志里点名是哪个 id
为什么这么狠
树还没立起来过，没有可回退的状态。一份装不上的配置只能失败得响亮
运行中

整次更新回滚，实例毫发无损

怎么发生
实例跑着，你往活层追加一条同 id 的 insert
判词
failed to apply loader entry include (cordis:include): duplicate loader entry id: greeter
树怎么样
一点没动。 原条目的状态序列停在 ['LOADING','ACTIVE']——连 DISPOSED 都没有
之后呢
进程照跑，再改一次代码照样热重载。一次失败的配置更新弄不坏这个实例

所以活层可以放心改。 改错了不会搞死跑着的实例——它退回上一个好状态，在事件流里留下一条 hmr/config-update-failed 和两条 warn，然后继续等你把它改对。
