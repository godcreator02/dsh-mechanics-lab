第零章 · 0-2 · 准备

这台仪器凭什么可信

从下一项开始，每一页的数字都出自同一台采集器。所以先把这台仪器本身查一遍： 它能听见什么、听不见什么。这两条不摆清楚，后面所有页面的数据都要打问号。

uv run pytest experiments/ch0_observer/ -n 0 -s · 3 个用例 · 约 5 秒

先说仪器

它凭什么能看见

要看清插件加载时发生了什么，得有个东西在进程里听着。这台采集器叫 lab-recorder，它本身就是一个普通插件条目——写在同一个 patch 文件里， 跟被观测的东西平级，没有任何特权。所以后面每张图里你都会看到它。

它怎么听见框架说话

// fiber 每次状态变化触发一次，带旧状态。
// 这是抓住 LOADING 这种几毫秒窄窗口的唯一办法 —— 轮询必然错过。
ctx.on("internal/status", (fiber, oldValue) => {
  push("status", {
    id:   fiber.entry?.options?.id,
    from: FIBER_STATE[oldValue],
    to:   FIBER_STATE[fiber.state],
  });
});

FIBER_STATE 那张数字→名字的表得手写死在代码里：它在 cordis 里是 TypeScript 的 const enum，编译后被内联成数字字面量， 运行时根本不存在这个对象，import 不到。

fiber 这个词第 3 项才会正经讲，这里不用管它是什么。 眼下只要知道：它是条目跑起来之后的那个东西—— 状态（PENDING / LOADING / ACTIVE）就长在它身上，所以听它的变化就等于听条目的变化。

它怎么让别的插件也能说话

// 框架事件只回答「框架对这个条目做了什么」，
// 回答不了「这个插件自己拿到了什么」—— 那只有插件自己知道。
ctx.provide("labObserver", {
  // 传一次自己的 ctx，采集器反查你在树上的 id ——
  // 比让插件自报名字可靠：它写死的名字未必等于条目 id
  for(callerCtx) {
    const who = whoOf(callerCtx);
    return (note, data) => push("report", { who, note, data });
  },
});

于是「插件说的」和「框架说的」进同一条流、共用一套时间轴——先后关系直接读得出来， 不用去拼两份数据。从下一项起，每个插件都会用到它。

第一件事

它听见的远不止自己那一摊

这一项的 patch 文件只写了两条：仪器本身，和一个专门放在旁边给它看的陪衬。 陪衬什么都不干，只在 apply 里借上面那个口子说一句话。

profiles/observer/cordis.patch.yml — 我们写的全部内容
# 0-2 · 一台仪器 + 一个陪衬
- insert:
    - id: lab-recorder
      name: lab-recorder
      config:
        out: "…/out/testhome/ch0_observer/events.jsonl"
        flushMs: 100

    - id: neighbor
      name: ./neighbor.mjs

跑出来

431条事件
81个条目被听见
2条是我们写的
79条我们一个字都没写过

这 431 条都是什么

status 状态变化204 plugin 条目建立100 snapshot 起点快照81 service 服务出现43 recorder 仪器自述2 report 插件说的话1

那 79 条里随手抽 20 个：
agent agent-default-model agent-instructions agent-loop approval attachment-local bash-sandbox command-compact command-feedback command-goal commands compaction-basic credentials fs-observation-policy fs-sandbox goal goal-round-driver hmr include jobs

它听的是整棵树，不是自己那一摊。 这是整套观测方案的地基——仪器要是只听得见自己写进 patch 文件的那两条， 后面每一页的数据都只能说明「采集器怎么样」，说明不了「实例里发生了什么」。

陪衬那条留下了什么

neighbor  走过的状态   PENDING → LOADING → ACTIVE
neighbor  说的话       "我跑起来了"   （+8.369ms）

两行读自同一条事件流、同一套时间轴。 上面那行是框架说的（它把这个条目挂起来了），下面那行是插件自己说的 （它跑到了自己那句话）——所以「谁先谁后」是直接读出来的，不是拼出来的。

第二件事

它自己也在树上，一点特权都没有

仪器不是挂在系统外面的探针。它占一个条目位、自己也走状态、这些状态还被它自己记了下来。 最直接的证据在起点快照里——那张快照是它在自己的 apply 里拍的， 而快照里有它自己：

events.jsonl 第 81 条 — 起点快照里的它自己
{ "seq": 80, "ms": 1.2392, "kind": "snapshot",
  "id": "lab-recorder", "name": "lab-recorder",
  "to": "LOADING", "hasFiber": true, "disabled": false,
  "config": { "out": "…/ch0_observer/events.jsonl", "flushMs": 100 } }

拍快照那一刻，它自己是 LOADING。 因为拍快照这个动作就发生在它自己被加载的过程中——它跟别人受同样的规则约束， 排在第几个也不由它说了算。随后它自己走到 ACTIVE，这一跳同样进了它自己写的那条流。

第三件事

它睁眼之前的历史，是丢的

采集器自己也要被加载。在它挂上之前发生的事，没有任何人记——框架不提供事件回放。 所以事件流的第一条永远是它给自己的一句交代： 

// events.jsonl 第 1 行
{ "seq": 0, "ms": 0.3337, "kind": "recorder",
  "note": "采集开始（本行之前的事件未被记录）" }

紧接着是起点快照：每个条目在它睁眼那一刻各自是什么样。 丢掉的仍然是过程，但起点是确切的。这一次快照拍到 81 个条目，分三档——

还没建起来
77
从建立到就绪，整条链一跳不缺
建起来了，还在等
2
还没开始跑，之后每一跳都记得到
已经在 LOADING
2
进 LOADING 那一跳发生在睁眼之前，永远补不回来

丢的是哪两条

              快照时      事件流里记到
include       LOADING     只有 → ACTIVE
lab-recorder  LOADING     只有 → ACTIVE

── 同一份数据里的对照组 ──────────────────────
neighbor      PENDING     → LOADING  → ACTIVE
agent         还没建起来   → LOADING  → ACTIVE

那两条里有一条就是采集器自己——这台仪器连自己的出生都没记全。 快照拍下的是它自己正在 LOADING，也就是说它进 LOADING 那一跳， 发生在它有能力记录之前。

这个上限没法靠调整书写顺序绕开：条目的加载顺序不由 patch 文件里的先后决定 ——下一项就会亲眼看到这件事。所以这一页起，凡是本站出现的毫秒数， 都相对采集器睁眼那一刻，不是进程启动。
